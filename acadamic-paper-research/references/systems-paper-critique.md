# 系统类论文的深度批评框架（Phase 4 / critique）

适用：网络、系统、体系结构会议论文（SC/NSDI/SIGCOMM/ASPLOS/HPCA…）。目标不是复述优缺点，而是给出**可被作者反驳检验的具体判断**，并把"论文明确陈述"与"我的推论"严格分开（用户明确要求这一区分）。

## 1. 数字溯源（最高价值的一步）

把摘要/引言里的每个 headline 数字，逐个回到图表读数核对：

- 摘要说 X×、正文说 Y%、图里能读出 Z —— 三者常常不一致。列出「声明值 / 图中可读值 / 口径（哪个负载、哪个分位、哪个丢包率）/ 是否一致」。
- 常见口径漂移：up-to 值取自最有利场景（HPC 归一化 p99），而微基准只有 2×；正文某处加速比与图中中位数差 15 个百分点以上。
- 不确定的推断必须写「此为推论，论文未明示出处」，不要写成事实。
- 同一数字在不同实验里含义不同（如"35% 加速"是集合通信 time，不是尾延迟），提醒读者不可相乘。

## 2. 消融读法：先找 2×2，再看单变量

优秀的系统论文会把一个机制拆成可控变量矩阵（如 corruption 有/无 × trimming 开/关；σ × τ）。读的时候问：

- 哪一格是"机制不占优"的？那一格往往最能说明贡献来源（例如开 trim + 无丢包时新方案并不领先 → 它赢在判丢而非负载均衡）。
- 消融表里最敏感的参数是哪个？其最优值对应的开销有没有被计量？（例：探针频率 P=1 把 RTO 从 2.6k 降到 48，但探针带宽开销全文未给 → 这是可用性缺口）
- 是否存在"双信令互扰"现象（新机制与既有机制同时开启时指标反而变差）？若论文未解释，直接列为待追问点。

## 3. 隐含契约（hidden contracts）

每个机制都依赖若干未被明说的前提，找出来并问"违约时怎么办"：

- 例：子流保序依赖"同一 EV 必走同一物理路径"，而目标生态（UE/AR）恰恰鼓励交换机自适应换路 → 契约失效后"确定性判丢"退化为启发式，且论文没有运行期违约检测。
- 其他常见契约：端主机可写某个包头字段；网络不重排某类包；接收端状态可随流数线性增长；时钟/定时器精度；单租户。
- 写法：「论文明确说…；我的推论：若…则…；论文未给出…」。

## 4. 评估现实性四问

1. 大规模结果来自真实 testbed 还是仿真？仿真的故障模型是否与物理机制同构（独立随机丢包 vs 突发/相关损坏）？
2. 硬件原型处于什么条件（loopback？无拥塞？RTO 设成 1 s？型号保密？）——能证明"可实现"还是能证明"有收益"？
3. 参数是否被调到有利值，且这些值在真实部署里可复现（如 σ=16、每子流 4096 个 EV）？
4. 缺哪些对照：同一生态最新的另一设计点是否只被一句话带过？是否有"理想 oracle"上界把两个收益源分开？

## 5. 可复现性表（固定模板）

| 项目 | 状态 | 说明 |
|------|------|------|
| 仿真器/代码 | 可获取 / 未提及 | 是否开源、是否给 artifact 链接 |
| 拓扑与参数 | 完整 / 部分 / 缺失 | 逐项列（节点数、链路速率、MTU、RTT、队列、丢包率、算法超参） |
| 随机性 | 说明充分 / 未说明 | seeds 数、跨 seed 方差 |
| 数据/trace | 公开 / 部分 / 私有 | 给 URL 或仓库名 |
| 硬件 | 可复现 / 不可复现 | 型号是否披露 |

结论句必须分开写「仿真部分 X，硬件部分 Y」，不要给一个笼统分数。

## 6. 输出结构（与 running_notes 的 9.x 对齐）

1. 关键实验数据速查表（拓扑/参数/各实验配置/收益/超时数）
2. 优势（3–7 条，每条要能指到具体章节或图表）
3. 不足（按 A–F 分组：评估模型 / 硬件验证 / 对照缺失 / 隐含契约 / 数字口径 / 理论支撑）
4. 开放问题（可直接立项，每条含"要做什么实验/要证什么"）
5. 可复现性表
6. 零散观察（命名、写作手法、资助结构、同期工作关系）
7. 一页结论：一句话 / 最硬的贡献 / 最硬的证据 / 最大的保留 / 最该追问的问题

## 7. 分寸

- 优点要具体到"哪张图的哪一格使这个论点成立"，否则就是套话。
- 不足要区分「作者已承认的局限」与「作者未意识到的缺口」——后者才是审稿价值所在。
- 不臆造缺陷：没读到的实验不能断言"没做"，只能写"正文未见"。
