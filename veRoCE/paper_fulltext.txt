1Overview
In the artificial intelligence (AI) era, RDMA (Remote Direct Memory Access) is widely used for
high‑speed, low‑latency data movement among GPUs or AI accelerators. InfiniBand (IB) RDMA
enablesefficientcommunicationoverInfiniBandnetworks,whileRoCEv2(RDMAoverConverged
Ethernet)extendsRDMAtoEthernet‑baseddatacenters. However,bothIBandRoCEv2requirea
losslessnetworktooperateeffectively,makingRDMAtransportprotocolsinefficientathandling
packet drops and out‑of‑order packet arrivals. Additionally, lossless network fabrics are prone
to congestion spreading and deadlocks, which severely limit network scale. As AI networks
will expand to support hundreds of thousands, or even millions, of GPUs or AI accelerators,
these limitations become more pronounced. At such a scale, packet drops and out‑of‑order
arrivals caused by multi‑path transmission and lossy networks are unavoidable ’facts’ that must
be addressed.
ThisspecificationdefinestheveRoCEtransportprotocol,asolutionthatmaintainsbackward
compatibility with RoCEv2 while introducing key extensions to enhance RDMA’s resilience to
packetdropsandout‑of‑orderarrivalsacrossalltransportsemantics. Byaddressingtheselimi‑
tations,veRoCEeliminatesRDMA’srelianceonalosslessnetwork. ThesuccessofRDMAlargely
comes from its well‑designed message semantics (e.g., RDMA READ/WRITE), packet formats,
and user interfaces (e.g., ibverbs). To preserve these strengths, veRoCE aims to minimize mod‑
ifications to the existing RDMA protocol while introducing only necessary enhancements.
Specifically,veRoCEfeaturesmulti‑pathtransmission,out‑of‑orderdelivery,efficientpacket
lossdetection,hardware‑friendlyselectiveretransmission,andflexiblecongestioncontrolforall
transport semantics. Multi‑path transmission in veRoCE can be achieved via changing packet
entropybythesourceendpoint(andrelyingonswitchECMP),orsprayingpacketsontheswitch.
Out‑of‑order data delivery is natively supported at the responder endpoint, as the data packets
contain extended headers to support DDP (Direct Data Placement), even for Send/Recv opera‑
tions. veRoCE implements selective acknowledgments (SACKs) to notify the sender of out‑of‑
orderpacketarrivals. Thismechanismenablesrapiddetectionofpacketlossandtriggersafast
selective retransmission algorithm that efficiently recovers lost packets while minimizing un‑
necessary retransmissions. Unlike IB/RoCE, where Read response packets consume PSNs from
the requester, veRoCE assigns a separate PSN space for Read responses at the responder side.
Upon receiving these responses, the requester sends corresponding ACKs or SACKs. This de‑
sign unifies the packet loss detection and fast retransmission mechanisms for both Send/Write
packets and Read responses. veRoCE provides a FCC (Flexible Congestion Control) framework
to allow incorporation of customized congestion control algorithms. It supports path‑wise or
connection‑wise, window‑based or rate‑based congestion control modes. In rate‑based con‑
gestioncontrol, itdecouplescongestioncontrolfromtransportreliability, whichmeansthecon‑
gestionsignalsareconveyedinseparatepacketsratherthanthecommonlyusedacknowledge‑
ment packets. Thus, the coalescing of acknowledgement packets on an endpoint will not be
interruptedbytherequirementtotransmitacongestionsignal. veRoCEalsosupportsunreliable
transmission, primarily for connection management packets. The communication interface that
veRoCE natively supports is libibverbs, upon which other high‑level APIs can be built.

2Terminology
Term Definition
QP (Queue Pair) A QP consists of a Send Queue (SQ) and a Receive Queue (RQ).
SQ and RQ are always created as a pair and remain that way
throughout their lifetime. A QP is identified by its QP Number.
Send Queue (SQ) A Work Queue, that contains descriptors (or WQEs, see below) for
outbound messages, including RDMA Read Request, RDMA Write
messages and Send messages, in the order as the descriptors are
posted from applications.
Receive Queue
(RQ)A Work Queue, that contains descriptors (or WQEs, see below)
that specify where to place inbound data.
Completion Queue
(CQ)A Work Queue, that contains Completion Queue Elements that
represent message completion. A CQ can be multiplexed across
multiple QPs.
Work Queue One of SQ, RQ, CQ.
Work Queue
Element (WQE)An item in the Work Queue, usually a descriptor for requests, data,
or message completion.
RQE Receive Queue Element, same as Receive Queue WQE.
Requester The QP that initiates the RDMA Read, RDMA Write and Send
operations. It sends out the request packets of RDMA Read,
RDMA Write and Send operations. It may more broadly represent
the thread, process, NIC or the host that this QP belongs to.
Responder The QP that accepts request packets of RDMA Read, RDMA Write
and Send operations, processes the messages, and returns
responses. It may more broadly represent the thread, process,
NIC or the host that this QP belongs to. Requester and responder
are usually used as a pair.
Request (Packet) Packets that require the receiving endpoint to process them (e.g.,
do DMAs) and generate response packets, generated by
requesters and received by responders. Request packets include
Read Request, Write Request, Send Request.
Response (Packet) Packets generated by a responder in response to the reception of
request packets. Response packets include acknowledgement
packets (see below) and Read Responses. Request and Response
are usually used as a pair.
Semantic Packet Packets that carry semantic meanings, including RDMA Read
Request, RDMA Read Response, RDMA Atomic Request, RDMA
AtomicAck, RDMA Write Request, and Send Request.
Acknowledgement
Packet (ack_pkt)Control packets used by a receiver (see below) to acknowledge
(positively or negatively) the semantic packets, including ACK,
NAK, and SACK packets. Semantic Packet and Acknowledgement
Packet are usually as a pair.

Term Definition
Sender Refer to the QP that sends semantic packets. It will receive
acknowledgement packets to ascertain the delivery of semantic
packets. Therefore, it is legal to use the phrase “A sender
transmits a Write request packet and then receives an ACK.”
Receiver Refer to the QP that receives semantic packets. It will transmit
acknowledgement packets to inform the sender about the arrival
of semantic packets. Therefore, it is legal to use the phrase “A
receiver receives a Write request packet and then transmits an
ACK.”
ACK Positive acknowledgement packet, used to ascertain the arrival of
one or more in‑order semantic packets (except Read Responses),
sent by receiver to sender.
SACK Selective Acknowledgement packet, used to selectively ascertain
the arrival of both in‑order and out‑of‑order semantic packets
(except Read Responses).
NAK Negative Acknowledgement packet, used to explicitly inform the
sender that one semantic packet (except Read Responses) has
been dropped, possibly dropped by a switch or a receiver (due to
insufficient resource).
ACK_Rsp Positive acknowledgement packet, used to ascertain the arrival of
one or more Read Response or AtomicAck packets, sent by
receiver to sender.
SACK_Rsp Selective Acknowledgement packet for Read Responses and
AtomicAck packets.
NAK_Rsp Negative Acknowledgement packet, used to explicitly inform the
sender that one Read Response or Atomic packet has been
dropped, possibly dropped by a switch or a receiver (due to
insufficient resource).
PSN (Packet
Sequence Number)A monotonically increasing sequence number assigned to
semantic packets by senders.
aPSN
(Acknowledgement
PSN)The most recent sequence number such that all packets with
PSNs less than or equal to this value have been received.
ePSN (Expected
PSN)The PSN of the next in‑order semantic packet that a receiver
expects to receive, i.e., aPSN + 1. This indicates that the packet of
ePSN must not have been received, and PSNs larger than ePSN
may have been received.
MSN (Message
Sequence Number)A monotonically increasing sequence number assigned to
messages initiated from both the requestor and the responder.
Request messages from the requestor and Response messages
from the responder are in the different MSN spaces.
aMSN
(Acknowledgement
Packet MSN)The most recent sequence number such that all messages with
MSNs less than or equal to this value have been received.

5ReliableConnectionService
ReliableConnection(RC)providesaguaranteethatsemanticpacketsaredeliveredfromaSender
to a Receiver at most once without corruption, in the presence of lossy networks and multi‑path
transmission.
With out‑of‑order packet arrivals, lost packets must be quickly identified and retransmitted.
To achieve this goal, key elements of the Reliable Connection service include a new PSN as‑
signment method for the RDMA Read operation, an acknowledgment mechanism allowing the
sender to ascertain that the semantic packets have been successfully delivered; packet and
message numbering mechanisms to allow the sender to correlate acknowledgement packets
with the semantic packets; heuristics in combination with packet numbering mechanism to de‑
tect missing packets under multi‑path; and eventually a timer to allow detection of dropped or
missing acknowledgment messages based on timeout.
NotethatCRCsarecheckedatlowerprotocollayersandmayresultinpacketsbeingdropped
before they are delivered to the transport layer.
To provide a clear understanding of the Reliable Connection service, this specification de‑
scribes the endpoint behaviors from both the Sender‑Receiver and Requester‑Responder per‑
spectives, as appropriate. Sender‑Receiver perspective is about the sending and receiving
of semantic packets and acknowledgements, while Requester‑Responder perspective is about
sending and receiving of requests and responses in terms of transport primitives.
5.1PSN
Each packet is transmitted with a PSN in its BTH. PSNs are used to identify missing or out‑of‑
order packets, and, for Reliable Connection service, to relate an acknowledge packet to a given
semantic packet. A sender assigns PSNs to newly created semantic packets. The PSN value
increases monotonically in one PSN space, and the initial value is negotiated during connection
establishment. There is a relationship between the PSN on a requester’s Send Queue and the
PSN on the responder’s corresponding QP (for Send, Write and Read Request primitives). Also,
there is a relationship between the PSN of Read Response/AtomicAck on a responder and the
PSNontherequester’scorrespondingQP(forReadResponses). Thus,aQP’soutboundpackets
are in two separate PSN spaces, each for Send Queue and Read Response/AtomicAck. Accord‑
ingly, a QP’s inbound packets are also in two separate PSN spaces. There is no relationship
between the PSNs used by the Send queue and Read Response/AtomicAck of a QP, or between
different connections.
Therearetwosituationsthatmustbedetectedandresolvedatthereceivertoensurereliable
operation꞉ duplicate packets and out‑of‑order packets.
•Duplicate Semantic Packet

into the fabric more than once. This occurs when the sender detects a condition for which the
prescribed recovery mechanism is to retry the operation. There are two primary causes for the
requester to inject duplicate semantic packets, both leading to a timeout. 1) Acknowledgement
packets are lost or delayed in the fabric for a very long time; 2) A semantic packet is delayed
in the fabric for a long time (but not lost) and there are no follow‑up semantic packets, then a
timeout will occur at the sender. Retransmitting the packets that are presumed lost will cause

The Acknowledgement Protocol, plus packet sequence numbers, are fundamental components

7.3CongestionControlModes
The congestion control mechanism for a Reliable Connection that employs multi‑path can op‑
erate in two modes꞉ connection‑wise and path‑wise. In either mode, the sender QP maintains
one or more Congestion Control Context (CCC) that controls the sending rate. Note that for
single‑path Reliable Connection, there is no need to distinguish between connection‑wise and
path‑wise mode. They are the same.
For sender‑spreading multi‑path transmission, the sender QP assigns different src ports to
semantic packets, and the switch ECMP hashes the packets onto different paths. In the path‑
wise mode, the sender QP uses a separate sending rate on each path, and the receiver QP
echos path‑wise congestion signal back to sender via CNPs. The CNPs for different paths are
distinguished by their UDP src ports associated with each path. The sending rate for each path
canbedeterminedeitherbyanindividualCCCdedicatedtothatpathorbyasingleconnection‑
wise CCC that allocates rates across paths using a weighted round‑robin scheme.
In the connection‑wise mode, the receiver QP does not discriminate the CNP from different
paths. The number of ECN‑marked packets from all the paths are cumulated onto one variable.
ThesenderQPusesonlyonesendingrateonallpaths. Thatis,thesenderQPonlycalculatesone
transmission rate, and it is evenly distributed on all the paths. This rate is expected to converge

to the lowest available rate among all the paths. In both path‑wise mode and connection‑wise
mode, the RTT probing is performed on a per‑path basis. This helps the requestor to identify
slow paths in the connection‑wise mode.
For multi‑path achieved by switch Adaptive Routing, the sender QP is unaware of the multi‑
path, and the receiver QP can not distinguish the packets from any path, therefore, connection‑

It is possible that different connections use different DSCP values to make use of the QoS

10Programmer’sGuidetoveRoCE
10.1OperationOrderingConsiderations
To minimize the effort required for developers to adopt veRoCE, most of its semantics align
closely with RoCEv2. However, therearetwo key differencesthat must be addressed꞉ First, due
to the use of DDP, applications cannot assume any ordering of data written to the responder’s
memory by RDMA Writes or Sends. On the requester side, no ordering guarantee exists for
data read via RDMA Reads. An application cannot determine the completion of a Send message
by inspecting the last byte of the receive buffer. The only reliable indication of completion is
the CQE of that message. Similarly, if an error CQE is posted for a message, the data from
subsequent messages may have been written to the responder’s memory.
Second, applications cannot assume the results of two RDMA Writes or Sends if they share
the same target memory and the second message is posted before the first completes. This is
because there is no ordering guarantee between Write and Send messages. If strict ordering
is required, it is recommended to set the fence indicator on the second message to enforce
operation ordering.
Aside from these two differences, applications can assume that veRoCE semantics are con‑
sistent with those of RoCEv2.
10.2EnhancedApplicationProgrammingInterfaces
veRoCEintroducesadvancedfeaturessuchasmulti‑pathandlazySACK,whichrequireconfigu‑
ration parameters not covered by the standard verbs API. Examples of such parameters include
the number of paths, the list of UDP source ports, and the lazy SACK threshold.
To ensure transparent adoption by existing applications utilizing the verbs interface, veRoCE
advocates a host‑based configuration approach. This approach preserves the existing verbs
interface unchanged, thereby eliminating the need for any modifications within the application
itself. Configuration APIs are provided via a separate, dedicated API library. These APIs are
intendedtobeinvokedbyamanagementprogram,independentfromtheapplicationprocesses.
The configuration APIs are designed to support both global settings (applicable to all Queue
Pairs) and granular, per‑Queue Pair configurations.
It is important to note that veRoCE does not prescribe a specific API design or implementa‑
tion. Should an application developer choose to modify the verbs interface, an implementation
may optionally incorporate configuration channels directly into the verbs API.
