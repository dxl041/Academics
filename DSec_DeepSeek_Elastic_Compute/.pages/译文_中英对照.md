## 1. Introduction

**EN:**
Recent advances in frontier LLMs have made agentic workflows practical and widely adopted (Guo et al., 2025; Jimenez et al., 2024; OpenAI et al., 2024). Instead of producing a single text answer, an agentic model interacts with an execution environment: it may navigate codebases, call tools, execute commands, inspect failures, and modify files, or operate browsers and desktop applications through graphical interfaces in computer-use tasks (Xie et al., 2024; Zhou et al., 2024). Across these workloads, the model iterates based on feedback until a task is solved. This execution model has led to a growing ecosystem of agent tools and orchestration harnesses, such as DeepSeek Harness (DSH) (Shi et al., 2026), OpenCode (Anomaly, 2025), and multi-agent training harnesses. Training reliable agents requires reinforcement learning (RL) at scale, in which models learn through interaction with real, isolated execution environments rather than solely from static input-output examples.

**CN:**
前沿 LLM 的近期进展使 agentic workflow 变得实用并被广泛采用（Guo et al., 2025; Jimenez et al., 2024; OpenAI et al., 2024）。agentic 模型不再只产出一段文本答案，而是与一个执行环境交互：它可能浏览代码库、调用工具、执行命令、检查失败原因、修改文件，或在 computer-use 任务中通过图形界面操作浏览器与桌面应用（Xie et al., 2024; Zhou et al., 2024）。在这些负载中，模型依据反馈反复迭代，直到任务被解决。这种执行模式催生了不断壮大的 agent 工具与编排 harness 生态，例如 DeepSeek Harness（DSH）（Shi et al., 2026）、OpenCode（Anomaly, 2025）以及多 agent 训练 harness。训练可靠的 agent 需要规模化的 reinforcement learning（RL），其中模型通过与真实、隔离的执行环境交互来学习，而非仅从静态的输入-输出样本中学习。

**EN:**
The agentic training pipeline encompasses environment and data construction, RL rollouts, reward computation, policy updates, and periodic evaluation. Among these stages, RL rollout and evaluation impose the highest pressure on the sandbox platform because they are large-scale, concurrent, and tightly coupled with the training loop. In RL (Guo et al., 2025; Ouyang et al., 2022), training proceeds as a feedback loop with three stages. First, during rollout, the current model interacts with the sandboxed environment: it reads files, issues tool calls, executes commands, observes outputs, and produces a trajectory for each task. Second, during reward computation, the framework scores the trajectory using native execution signals such as exit codes, stdout, test pass rates, or task-specific verifiers. Third, during policy update, the RL algorithm updates the model parameters from the collected trajectories and rewards. Periodic evaluation follows a similar execution path, except that the resulting trajectories are used to measure model capability rather than to update parameters. Recent systems further pipeline generation and policy optimization through asynchronous rollouts, continuously replenishing completed samples to maintain high concurrency and mitigate long-tail stragglers (DeepSeek-AI, 2026). For agentic workloads, this design keeps many stateful sandbox sessions in flight and may interrupt and resume their associated rollouts across policy updates or scheduler preemptions, further increasing the platform's concurrency, lifecycle-management, and state-consistency requirements.

**CN:**
agentic 训练流水线包括环境与数据构建、RL rollout、reward 计算、policy 更新以及周期性评估。在这些阶段中，RL rollout 与评估对 sandbox 平台造成的压力最大，因为它们是大规模、并发的，并且与训练循环紧密耦合。在 RL 中（Guo et al., 2025; Ouyang et al., 2022），训练以包含三个阶段的反馈循环推进。第一，在 rollout 阶段，当前模型与 sandbox 化的环境交互：读取文件、发出工具调用、执行命令、观察输出，并为每个任务产出一条 trajectory。第二，在 reward 计算阶段，框架使用原生执行信号（如退出码、stdout、测试通过率或任务特定的 verifier）为 trajectory 打分。第三，在 policy 更新阶段，RL 算法利用收集到的 trajectory 与 reward 更新模型参数。周期性评估走类似的执行路径，区别在于产生的 trajectory 用于衡量模型能力而不是更新参数。近期系统进一步通过异步 rollout 把生成与 policy 优化流水化，持续补充已完成的样本以维持高并发并缓解长尾 straggler（DeepSeek-AI, 2026）。对 agentic 负载而言，这种设计使大量有状态的 sandbox 会话同时在飞，并可能在 policy 更新或调度器抢占期间中断并恢复其对应的 rollout，从而进一步提高平台在并发、生命周期管理和状态一致性方面的要求。

**EN:**
For each rollout or evaluation task, the platform must materialize an isolated task-specific environment, including its repositories, dependencies, services, evaluation scripts, and coding harnesses. The environment must be close enough to a real machine to run unmodified software stacks, package managers, build tools, browsers, emulators, and task-specific services. A robust, high-throughput sandbox runtime is therefore foundational for obtaining accurate and verifiable RL and evaluation results.

**CN:**
对每个 rollout 或评估任务，平台都必须实际构建出一个隔离的、任务特定的环境，其中包含该任务的代码仓库、依赖、服务、评估脚本和编码 harness。该环境必须足够接近真实机器，才能运行未经修改的软件栈、包管理器、构建工具、浏览器、模拟器以及任务特定服务。因此，一个健壮、高吞吐的 sandbox runtime 是获得准确且可验证的 RL 与评估结果的基础。

**EN:**
Agentic sandbox workloads have several properties that shape the platform design:

**CN:**
agentic sandbox 负载具有若干塑造平台设计的特性：

**EN:**
(1) Rollout and evaluation jobs create sandboxes in a bursty manner. A single job may request up to 32K sandbox instances, so the platform must accept and place many sandboxes concurrently. Such bursts make horizontal scalability a system-wide requirement and require shared services, such as scheduling and image distribution, to avoid centralized bottlenecks.

**CN:**
(1) rollout 与评估作业以突发方式创建 sandbox。单个作业最多可能请求 32K 个 sandbox 实例，因此平台必须能并发接收并放置大量 sandbox。这种突发性使水平可扩展性成为全系统级的要求，并要求调度、镜像分发等共享服务避免出现集中式瓶颈。

**EN:**
(2) Sandboxes must run at high density. During agent interaction, a sandbox often waits for the LLM to generate the next action, so CPU usage is sparse and naturally suitable for overcommit. For instance, in production, this allows a single node to host up to 800 microVMs or 3,200 containers, but only if the platform can safely overcommit resources and manage lifecycle pressure at node scale.

**CN:**
(2) sandbox 必须以高密度运行。在 agent 交互过程中，sandbox 常常在等待 LLM 生成下一步动作，因此 CPU 使用率稀疏，天然适合 overcommit。例如在生产中，这使单个节点最多可承载 800 个 microVM 或 3,200 个 container，但前提是平台能够在节点规模上安全地超卖资源并管理生命周期压力。

**EN:**
(3) Agent sandboxes are stateful and long-lived. The model may modify files, install dependencies, and start services, and later tool calls depend on this accumulated state. Since a sandbox can stay alive across many LLM interaction turns, memory footprint, guest page cache, host page cache, and writable state may remain pinned long after the CPU becomes idle. Under high-density overcommit, these resident costs directly limit cluster capacity, so memory sharing and reclamation become important platform requirements.

**CN:**
(3) agent sandbox 是有状态且长生命周期的。模型可能修改文件、安装依赖、启动服务，后续的工具调用依赖这些累积的状态。由于一个 sandbox 可以跨越许多 LLM 交互轮次持续存活，内存占用、guest page cache、host page cache 以及可写状态可能在 CPU 早已空闲之后仍被长期占用。在高密度 overcommit 下，这些常驻开销直接限制集群容量，因此内存共享与回收成为重要的平台需求。

**EN:**
(4) Agent workloads are highly heterogeneous. The platform must cover OJ-like script execution, software-engineering tasks over full repositories, security tasks, computer-use workloads, mobile development environments (e.g., Android), and other full-system environments. These workloads differ substantially in CPU and memory demand, dependency footprint, required system functionality, and isolation strength. A single sandbox abstraction cannot cover all of them efficiently. For example, lightweight function calls are preferable for short stateless tasks, whereas virtual machines (VMs) are better suited to workloads that require a complete commercial off-the-shelf operating system.

**CN:**
(4) agent 负载高度异构。平台必须覆盖类 OJ 的脚本执行、针对完整代码仓库的软件工程任务、安全任务、computer-use 负载、移动开发环境（如 Android）以及其他全系统环境。这些负载在 CPU 与内存需求、依赖足迹、所需系统功能以及隔离强度上差异很大。单一的 sandbox 抽象无法高效覆盖所有负载。例如，对短小的无状态任务，轻量的函数调用更合适；而对需要完整商用现成操作系统的负载，virtual machine（VM）更合适。

**EN:**
(5) Environment diversity is high even within the same workload class. Training and evaluation corpora contain many tasks, and each task may require its own repository, dependency versions, services, toolkits, evaluation scripts, or VM snapshots. As a result, the platform must serve a large number of distinct images and environment artifacts, with limited reuse for many of them. Under bursty startup, fetching these diverse task images from a registry would concentrate load on the distribution path, inflate startup latency, and introduce extra I/O that interferes with already-running sandboxes. In our ablation, eager image pulling stretches completion time by 1.7×, while on-demand loading reduces cumulative disk writes by 57%.

**CN:**
(5) 即使在同一个负载类别内，环境多样性也很高。训练与评估语料包含大量任务，每个任务可能都需要自己的代码仓库、依赖版本、服务、工具包、评估脚本或 VM 快照。因此平台必须服务大量各不相同的镜像与环境产物，其中许多的复用率有限。在突发启动下，从 registry 拉取这些多样化任务镜像会把负载集中在分发路径上，抬高启动延迟，并引入额外 I/O 干扰已在运行的 sandbox。在我们的消融实验中，eager image pulling 使完成时间延长 1.7×，而 on-demand loading 将累计磁盘写入减少 57%。

**EN:**
(6) Agent execution is untrustworthy. Agents may corrupt filesystems, exhaust resources, or interfere with system components, potentially disrupting rollouts or other co-located workloads. The platform therefore requires fine-grained access control and misbehavior analysis to contain and diagnose agent-induced failures.

**CN:**
(6) agent 的执行不可信。agent 可能破坏文件系统、耗尽资源或干扰系统组件，从而潜在地打断 rollout 或其他同机共置的负载。因此平台需要细粒度的访问控制与异常行为分析，以约束并诊断 agent 引发的故障。

**EN:**
(7) Agent execution is interruptible. GPU training jobs may be preempted while long-running rollouts are still in progress. The platform must therefore preserve execution state and support efficient recovery across interruptions.

**CN:**
(7) agent 的执行可被中断。GPU 训练作业可能在长时间运行的 rollout 尚未结束时就遭到抢占。因此平台必须保存执行状态，并支持跨中断的高效恢复。

**EN:**
These properties define the role of an agent sandbox platform. DSec provides elastic service scaling, high-density resource management, memory sharing and reclamation, multiple isolation mechanisms for different workload classes, scalable image distribution, and explicit integration with the training framework for preemption-safe resumption, task-specific network policy, and agent misbehaving mitigation.

**CN:**
这些特性界定了 agent sandbox 平台的角色。DSec 提供弹性服务伸缩、高密度资源管理、内存共享与回收、面向不同负载类别的多种隔离机制、可扩展的镜像分发，以及与训练框架的显式集成，从而支持抢占安全的重续、任务特定的网络策略以及 agent 异常行为的缓解。

## 2. Overview of DSec

**EN:**
This chapter presents the user-facing view of DSec. From the platform's perspective, users are the training frameworks, evaluation frameworks, and data-construction pipelines that call the software development kit (SDK) on behalf of researchers; we refer to them collectively as users throughout the report. It covers the SDK entry point, the sandbox backends exposed by the platform and the workload classes they serve, the lifecycle of a sandbox session, and the operating scale of the production deployment.

**CN:**
本章给出 DSec 面向用户的视图。从平台的角度看，用户是代表研究者调用 software development kit（SDK）的训练框架、评估框架与数据构建流水线；本报告中我们统称它们为用户。本章涵盖 SDK 入口、平台对外暴露的 sandbox backend 及其服务的负载类别、一个 sandbox 会话的生命周期，以及生产部署的运行规模。

### 2.1 SDK Entry Point

**EN:**
Users access DSec through libdsec, a Python client library for the sandbox service. libdsec gives users a unified SDK entry point for creating and operating sandboxes, while still requiring them to choose the sandbox backend appropriate for the task. A typical request specifies the sandbox type, image or environment identifier, CPU and memory limits, lifetime settings, network rules, and initial user context. After creation, the user can execute shell commands or tool calls and collect command outputs and return status. List. 1 shows a minimal container session: the client connects to the service endpoint, requests a sandbox with the desired resource and network policy, runs a command, and releases it.

**CN:**
用户通过 libdsec 访问 DSec，这是一个面向 sandbox 服务的 Python 客户端库。libdsec 为用户提供创建和操作 sandbox 的统一 SDK 入口，但仍要求用户自行选择适合该任务的 sandbox backend。一个典型请求会指定 sandbox 类型、镜像或环境标识、CPU 与内存上限、生命周期设置、网络规则以及初始用户上下文。创建之后，用户可以执行 shell 命令或工具调用，并收集命令输出与返回状态。List. 1 展示了一个最小的 container 会话：客户端连接服务端点，请求一个具备所需资源与网络策略的 sandbox，运行一条命令，然后释放它。

Listing 1 | A minimal sandbox session through libdsec.（通过 libdsec 的最小 sandbox 会话）

```python
client = DSecClient()
await client.open()
args = DSecContainerRunArgs(
    container_image="registry.../sphinx-9658:official",
    memory_limit_mb=4096, cpu_cores_limit=4,
    ttl_running_stop=300,
    # idle timeout
    network_rules={"npm": False, "pypi": True},
    init_user="root",
)
sandbox = await client.run_container(args, timeout=120)
result = await sandbox.run_shell("echo hello world")
await sandbox.stop()
```

**EN:**
In this example, the network rules allow access to PyPI (pypi=True) but deny access to NPM (npm=False). This fine-grained network control is discussed in detail in §6. This interface is intentionally not a full semantic abstraction over all backends. Function calls, containers, microVMs, and full VMs have different startup costs, isolation boundaries, filesystem semantics, and operating-system capabilities. libdsec provides a unified access path and a similar operational model, but the caller remains responsible for selecting a backend that matches the workload.

**CN:**
在这个例子中，网络规则允许访问 PyPI（pypi=True）但拒绝访问 NPM（npm=False）。这种细粒度网络控制在 §6 中详述。该接口有意不做过所有 backend 的完整语义抽象。函数调用、container、microVM 与 full VM 在启动开销、隔离边界、文件系统语义和操作系统能力上都不同。libdsec 提供统一的访问路径与相近的操作模型，但调用方仍需负责选择与负载匹配的 backend。

### 2.2 Sandbox Backends

**EN:**
Sandbox runtimes face a fundamental tension: stronger isolation and more complete system functionality usually come with higher startup latency and resource overhead. Since no single sandbox abstraction fits all agentic tasks, DSec supports multiple backends spanning this tradeoff space. Tab. 1 summarizes their typical fit.

**CN:**
sandbox runtime 面临一个根本性的张力：更强的隔离与更完整的系统功能通常伴随更高的启动延迟与资源开销。由于没有单一 sandbox 抽象能适配所有 agentic 任务，DSec 支持多个覆盖这一权衡空间的 backend。Tab. 1 汇总了它们的典型适用范围。

**EN:**
FnCall targets short, stateless tasks such as OJ workloads, code compilation, serverless programs, GPU kernels, and utility code. FnCall tasks run in reusable precreated CPU or GPU containers, avoiding per-invocation provisioning overhead. For GPU workloads, FnCall supports (i) shared mode, where multiple containers share a GPU instance, maximizing utilization for lightweight workloads, and (ii) exclusive mode, where one container reserves a GPU instance during its lifecycle for performance-sensitive tasks (e.g., operator evaluation). Containers are the main backend for software-engineering and general tool-use workloads. They provide fast startup and high packing density, and they run the Linux software stacks used by most repository-level tasks. Their main limitation is that they share the host kernel, which is not always appropriate for security-sensitive tasks. Firecracker microVMs (Agache et al., 2020) provide a stronger isolation boundary while retaining Linux compatibility. They are useful for security-sensitive tasks, stronger tenant isolation, and workloads that need a VM boundary with Linux compatibility. This comes at higher memory overhead and slower startup than containers.

**CN:**
FnCall 面向短小的无状态任务，例如 OJ 负载、代码编译、serverless 程序、GPU kernel 与工具代码。FnCall 任务运行在可复用的、预先创建的 CPU 或 GPU container 中，避免每次调用的供给开销。对 GPU 负载，FnCall 支持 (i) shared 模式，即多个 container 共享一个 GPU 实例，为轻量负载最大化利用率；以及 (ii) exclusive 模式，即一个 container 在其生命周期内独占一个 GPU 实例，用于性能敏感的任务（如算子评估）。Container 是软件工程与通用工具使用负载的主要 backend。它们启动快、打包密度高，并能运行大多数仓库级任务所使用的 Linux 软件栈。其主要局限是共享宿主机内核，因此并不总是适合安全敏感的任务。Firecracker microVM（Agache et al., 2020）在保持 Linux 兼容性的同时提供了更强的隔离边界。它们适用于安全敏感任务、更强的租户隔离，以及需要 VM 边界又需 Linux 兼容性的负载。代价是比 container 更高的内存开销与更慢的启动。

**EN:**
Full VM backends cover workloads that require a complete commercial off-the-shelf operating system environment, such as Android VMs through QEMU (Bellard, 2005), as well as those that require a GUI or graphics rendering. These backends have the highest resource overhead, but they are necessary for tasks that depend on OS-specific APIs, mobile runtime behavior, or full-system execution.

**CN:**
Full VM backend 覆盖需要完整商用现成操作系统环境的负载，例如通过 QEMU 运行的 Android VM（Bellard, 2005），以及需要 GUI 或图形渲染的负载。这些 backend 的资源开销最高，但对依赖 OS 特定 API、移动端运行时行为或全系统执行的任务是必需的。

**EN:**
In production, containers and microVMs dominate both instance count and resource consumption. FnCall serves a large number of lightweight invocations with a small set of resident environments, while full VM backends cover specialized but important workload classes.

**CN:**
在生产中，container 与 microVM 在实例数量和资源消耗上都占主导。FnCall 以少量常驻环境服务大量轻量调用，而 full VM backend 覆盖专门但重要的负载类别。

### 2.3 User-Visible Lifecycle

**EN:**
Although the supported backends differ internally, users see a unified high-level lifecycle. First, the caller creates a sandbox by selecting a backend and specifying the environment artifact, resource limits, lifetime policy, and network policy. The environment artifact varies by backend and workload. For containers and microVMs, it is a base image together with task-specific workspace and toolkit layers, which the platform composes into the running environment. For full VM workloads, it is a prepared VM image or snapshot. For FnCall, it is a task specification containing the task type, dependency files, and the code or script to run. These artifacts become the basis for the environment composition and image-distribution mechanisms discussed later in the report. Second, the platform prepares the environment and makes it ready for interaction. Third, the user issues commands or tool calls, observes outputs, and runs task-specific checks or tests. A sandbox is stateful throughout its lifetime: file edits, installed dependencies, and started services persist across calls, so later commands observe the effects of earlier ones. Because a sandbox stays alive across many interaction turns while its CPU is often idle between them, its resident state remains pinned long after the last command, one of the high-density challenges characterized in §4. Finally, the sandbox is stopped explicitly or reclaimed once its time-to-live elapses, so that idle or abandoned sessions do not hold resources indefinitely.

**CN:**
尽管所支持的 backend 在内部各不相同，用户看到的是一个统一的高层生命周期。第一，调用方通过选择 backend 并指定环境产物、资源上限、生命周期策略与网络策略来创建 sandbox。环境产物因 backend 与负载而异。对 container 与 microVM，它是基础镜像连同任务特定的 workspace 与工具包层，平台将其组装成运行环境。对 full VM 负载，它是预先准备好的 VM 镜像或快照。对 FnCall，它是包含任务类型、依赖文件以及待运行代码或脚本的任务描述。这些产物构成本报告后文讨论的环境组装与镜像分发机制的基础。第二，平台准备环境并使其就绪可交互。第三，用户发出命令或工具调用、观察输出，并运行任务特定的检查或测试。sandbox 在其整个生命周期内都是有状态的：文件修改、已安装的依赖与已启动的服务在多次调用之间持续存在，因此后续命令能观察到先前命令的效果。由于一个 sandbox 会在许多交互轮次中持续存活，而其间 CPU 常常空闲，其常驻状态在最后一条命令之后很久仍被占用——这是 §4 刻画的高密度挑战之一。最后，sandbox 会被显式停止，或在其 time-to-live 到期后被回收，以免空闲或被遗弃的会话无限期占用资源。

### 2.4 Deployment Scale

**EN:**
DSec is deployed across multiple scale units that share a 3FS (DeepSeek-AI) distributed file system deployment for base images and workspace storage. Within one scale unit, the platform spans nearly 160 CPU nodes with 30K cores and ~250 TB of DRAM. It manages petabytes of layers and images. On a typical day, a single scale unit serves about 3 M sandbox instances, with peak concurrency reaching ~380K and a creation rate exceeding 5,000 instances per second.

**CN:**
DSec 跨多个 scale unit 部署，这些 scale unit 共享一套用于基础镜像与 workspace 存储的 3FS（DeepSeek-AI）分布式文件系统部署。在一个 scale unit 内，平台覆盖近 160 个 CPU 节点、30K 核以及 ~250 TB 的 DRAM。它管理着 PB 级的层与镜像。在典型的一天里，单个 scale unit 服务约 3 M 个 sandbox 实例，峰值并发达到 ~380K，创建速率超过每秒 5,000 个实例。

**EN:**
These numbers are important for understanding the rest of the report. DSec is not a single sandbox runtime or a thin wrapper around containers. It is a production execution platform that must combine user-facing sandbox abstractions, backend-specific runtimes, scalable image storage, high-density resource management, and training-framework integration.

**CN:**
这些数字对理解本报告余下内容很重要。DSec 不是单一的 sandbox runtime，也不是对 container 的一层薄封装。它是一个生产级执行平台，必须把面向用户的 sandbox 抽象、各 backend 特定的 runtime、可扩展的镜像存储、高密度资源管理以及训练框架集成结合在一起。

## 3. Platform Architecture

**EN:**
§2 presented DSec as users see it: an SDK, a set of sandbox backends, and a session lifecycle. This chapter turns to the platform behind that interface and describes how a request travels from the SDK to a running sandbox and which components it passes through. We describe the architecture in terms of cluster-level services and the sandbox runtime. Cluster-level services provide request ingress, identity and access management, sandbox placement, and a view of cluster health and load. The sandbox runtime handles node-local admission, sandbox creation, execution, and resource reclamation, relying on 3FS for image data.

**CN:**
§2 从用户视角介绍了 DSec：一个 SDK、一组 sandbox 后端，以及一套会话生命周期。本章转向该接口背后的平台，描述一个请求如何从 SDK 走到正在运行的 sandbox，以及途中经过哪些组件。我们按 cluster-level services 与 sandbox runtime 两部分来阐述这一架构。Cluster-level services 提供请求入口、身份与访问管理、sandbox 放置，以及集群健康与负载视图。Sandbox runtime 负责节点本地的准入、sandbox 创建、执行与资源回收，并依赖 3FS 提供镜像数据。

### 3.1. Overview

> 图 1：DSec 架构总览。最上层是 libdsec（面向 Sandbox 的统一 Python SDK）与三类 sandbox 后端，管理请求与数据请求向下进入 cluster-level services（IAM、apiserver、placement engine、watcher），再下发到每个节点上的 runtime（edge、aether、chronus），最终落到 container / microVM / FullVM / FnCall 四类后端；镜像由 3FS 提供，容器与 VM 沙箱的通信都经由各自的 proxy 中转，FnCall 走单独的执行路径。图中标注了创建/删除控制流、隔离机制（AppArmor + eBPF）以及 EROFS / OverlayBD 镜像格式。

**EN:**
At a high level, a sandbox creation request is first sent to IAM for authentication and authorization. Once authorized, the request proceeds to the placement engine, which selects a target node using health and load information collected by the watcher. After placement, the apiserver forwards the request to the edge on that node. The edge then checks local capacity, creating the sandbox with the requested backend if capacity permits and rejecting the request otherwise. Image data needed by the sandbox is stored in 3FS and fetched on demand during startup and execution. Container, microVM, and full VM sandboxes run a per-sandbox proxy (aether) and one or more chronus instances for command execution, filesystem access, and other runtime operations. After one of these sandboxes is running, its operations are routed through the apiserver, edge, aether, and chronus. FnCall, by contrast, uses neither aether nor chronus and follows a separate request path: the submitted task is executed directly in a precreated container, followed by best-effort cleanup of task state.

**CN:**
从高层看，一个 sandbox 创建请求首先被送到 IAM 做认证与授权。授权通过后，请求进入 placement engine，后者利用 watcher 收集的健康与负载信息选出一个目标节点。完成放置后，apiserver 把请求转发给该节点上的 edge。edge 随即检查本地容量：容量允许就以请求的后端创建 sandbox，否则拒绝该请求。sandbox 所需的镜像数据存放在 3FS 中，在启动与执行期间按需拉取。Container、microVM 与 full VM 沙箱会运行一个 per-sandbox proxy（aether）以及一个或多个 chronus 实例，用于命令执行、文件系统访问及其他运行时操作。这类 sandbox 一旦运行起来，其操作就要经过 apiserver、edge、aether、chronus 逐层路由。相比之下，FnCall 既不使用 aether 也不使用 chronus，而是走另一条请求路径：提交的任务直接在预先创建的 container 中执行，随后对任务状态做尽力而为的清理。

### 3.2. Cluster-Level Services

**EN:**
Cluster-level services manage access to the platform and coordinate sandbox requests across compute nodes. They comprise IAM, the apiserver, the placement engine, and the watcher.

**CN:**
Cluster-level services 负责管理平台访问，并在各计算节点之间协调 sandbox 请求。它们由 IAM、apiserver、placement engine 和 watcher 组成。

**EN:**
IAM. Identity and Access Management (IAM) authenticates callers and authorizes all management requests to DSec. For example, requests to create or delete sandboxes or change a user's resource or concurrency limits must pass IAM checks before execution. A principal is the user or service identity associated with a management request. IAM uses projects to define scopes for resource management and access control. Within a project, access policies specify which principals may perform which management operations on its resources, while resource quotas limit resource consumption.

**CN:**
IAM。Identity and Access Management（IAM）对调用方进行认证，并对所有发往 DSec 的管理请求做授权。例如，创建或删除 sandbox、修改用户的资源或并发上限等请求，在执行前都必须通过 IAM 检查。principal 指与某个管理请求相关联的用户或服务身份。IAM 用 project 来界定资源管理与访问控制的作用域。在一个 project 内，access policy 规定哪些 principal 可以对其资源执行哪些管理操作，而 resource quota 则限制资源消耗。

**EN:**
We support multi-level project nesting rather than the flat or two-level hierarchies common in cloud platforms. Authorized principals, including agents and harnesses, can create subprojects, delegate part of the parent quota, and grant management permissions within them. Delegation is bounded by the parent: a principal cannot grant permissions it does not hold, and subproject policies and quotas cannot exceed the parent's access-control or resource limits. Humans and agents use the same management API and authorization model.

**CN:**
我们支持多级 project 嵌套，而非云平台中常见的扁平或两级层级结构。被授权的 principal（包括 agent 与 harness）可以创建 subproject、把父级 quota 的一部分下放，并在其中授予管理权限。委派受父级约束：principal 不能授予自己并不持有的权限，subproject 的 policy 与 quota 也不能超出父级的访问控制或资源上限。人类与 agent 使用同一套管理 API 和授权模型。

**EN:**
API Server. The apiserver serves as the ingress proxy for the sandbox cluster. Training and evaluation code invokes libdsec from trusted GPU servers, while sandboxes execute untrusted model-generated code and may access external networks. The two sides are therefore network-isolated, with the apiserver as the only permitted communication path. All sandbox requests, including creation, command execution, and streaming I/O, pass through this ingress. The apiserver maintains no per-sandbox state. It periodically refreshes the set of edge nodes from the watcher, while each sandbox ID encodes its owning edge. Any apiserver instance can therefore resolve and forward a request directly to the target edge, enabling the ingress tier to scale horizontally.

**CN:**
API Server。apiserver 是 sandbox 集群的入口代理。训练与评测代码从可信的 GPU 服务器上调用 libdsec，而 sandbox 执行的是不可信的模型生成代码，且可能访问外部网络。因此两侧在网络上是隔离的，apiserver 是唯一被允许的通信路径。所有 sandbox 请求——包括创建、命令执行与流式 I/O——都经过这一入口。apiserver 不维护任何 per-sandbox 状态。它定期从 watcher 刷新 edge 节点集合，而每个 sandbox ID 本身就编码了其所属的 edge。于是任意一个 apiserver 实例都能解析请求并直接转发到目标 edge，使入口层可以水平扩展。

**EN:**
Placement Engine. The placement engine selects a host node for each new sandbox. Placement proceeds in two stages: filtering and ranking. The filtering stage retains only healthy nodes that provide the backend and hardware capabilities required by the request. For example, a request for a GPU-enabled sandbox is restricted to nodes equipped with the required GPUs. The ranking stage randomly samples a few eligible nodes and selects the least loaded among them.

**CN:**
Placement Engine。placement engine 为每个新建 sandbox 选择主机节点。放置分两个阶段进行：filtering 与 ranking。filtering 阶段只保留健康、且具备请求所需后端与硬件能力的节点。例如，请求 GPU sandbox 时，候选范围被限制在配备所需 GPU 的节点上。ranking 阶段随机采样若干合格节点，并从中选出负载最低的一个。

**EN:**
Watcher. The placement engine's decisions are only as good as its view of the fleet, which the watcher provides. The watcher periodically probes the health of each edge and host and collects scheduling-relevant state, such as the number of running sandboxes across backend types, broken down per edge, per user, and per task. The placement engine periodically pulls this state from the watcher and uses the latest view when evaluating new creation requests. Please note that neither the placement engine nor the watcher requires durable state. The placement engine keeps no sandbox execution state, and the watcher can rebuild its fleet view after a restart by polling the edges again. This makes placement engine and watcher instances easy to add or replace without a costly recovery step.

**CN:**
Watcher。placement engine 的决策质量取决于它对整个机群的视图，而这一视图由 watcher 提供。watcher 定期探测每个 edge 与主机的健康状况，并收集与调度相关的状态，例如按后端类型划分的运行中 sandbox 数量，并按 edge、按用户、按任务细分。placement engine 定期从 watcher 拉取这些状态，在评估新的创建请求时使用最新视图。需要注意，placement engine 与 watcher 都不需要持久状态。placement engine 不保存任何 sandbox 执行状态，watcher 则可以在重启后通过重新轮询各 edge 重建机群视图。这使得 placement engine 与 watcher 实例易于增加或替换，无需付出高昂的恢复代价。

### 3.3. Sandbox Runtime

**EN:**
The sandbox runtime creates and operates individual sandboxes and manages their resources. It includes edge, aether, and chronus, and relies on 3FS for shared image storage.

**CN:**
sandbox runtime 负责创建与运行单个 sandbox 并管理其资源。它包含 edge、aether 与 chronus，并依赖 3FS 作为共享镜像存储。

**EN:**
Edge. Each node runs an edge, a per-machine component that handles creation requests from the apiserver for container, microVM, QEMU-based full VM, and FnCall backends. Before accepting a creation request, the edge checks the node's current capacity and rejects the request if capacity is insufficient. This node-local admission check complements the placement engine's placement decision, which is based on periodically refreshed cluster state. During creation, the edge provisions storage, applies the eBPF-based network policy, and launches the runtime.

**CN:**
Edge。每个节点运行一个 edge，这是一个按机器部署的组件，负责处理来自 apiserver 的 container、microVM、基于 QEMU 的 full VM 以及 FnCall 后端的创建请求。在接受创建请求之前，edge 会检查节点当前容量，容量不足则拒绝该请求。这一节点本地准入检查与 placement engine 基于定期刷新的集群状态所做的放置决策互为补充。创建过程中，edge 负责准备存储、施加基于 eBPF 的网络策略，并启动运行时。

**EN:**
FnCall and containers run inside QEMU/libvirt VMs rather than directly on the host. The VM provides an isolated kernel and network stack and serves as an additional security boundary between untrusted containers and the bare metal. To better support graphics-intensive workloads, such as computer-use GUI applications, browsers, video games, and 3D rendering, we leverage para-virtualized GPU interfaces of the host hypervisor (e.g., virtio-gpu). Within the full VM, we support both workloads whose graphics APIs are natively compatible with the host OS, as well as those whose rendering stacks can be translated into host-native APIs through compatibility layers such as DXVK (DXVK, 2018).

**CN:**
FnCall 与 container 运行在 QEMU/libvirt VM 内，而不是直接跑在宿主机上。VM 提供隔离的内核与网络栈，构成不可信 container 与裸金属之间的额外安全边界。为更好地支持图形密集型负载，例如 computer-use 的 GUI 应用、浏览器、视频游戏与 3D 渲染，我们利用宿主 hypervisor 的 para-virtualized GPU 接口（如 virtio-gpu）。在 full VM 内，我们既支持图形 API 与宿主 OS 原生兼容的负载，也支持其渲染栈可经由 DXVK（DXVK, 2018）等兼容层转换为宿主原生 API 的负载。

**EN:**
Besides tracking the sandbox lifecycle, edge coordinates disk and memory snapshots and releases node-local resources when the sandbox stops or its TTL expires.

**CN:**
除跟踪 sandbox 生命周期外，edge 还负责协调磁盘与内存快照，并在 sandbox 停止或 TTL 到期时释放节点本地资源。

**EN:**
Aether. Container and VM sandboxes run aether, a cross-platform proxy that establishes a communication channel with the edge. This edge-to-aether channel uses a platform-specific transport, such as a Unix domain socket for Linux containers or vsock for VM backends. The edge monitors sandbox health through the channel and marks the sandbox as failed if the channel closes. For each operation, aether uses the operation's terminal-session identifier to create or locate the corresponding chronus instance, then forwards the operation over the local channel. When the session ends, aether terminates the corresponding chronus process tree.

**CN:**
Aether。Container 与 VM 沙箱会运行 aether，这是一个跨平台 proxy，负责与 edge 建立通信通道。这条 edge 到 aether 的通道使用与平台相关的传输方式，例如 Linux container 用 Unix domain socket，VM 后端用 vsock。edge 通过该通道监控 sandbox 健康状况，通道一旦关闭就把 sandbox 标记为失败。对每个操作，aether 用该操作的 terminal-session 标识来创建或定位对应的 chronus 实例，然后经本地通道转发该操作。会话结束时，aether 终止对应的 chronus 进程树。

**EN:**
Chronus. chronus provides a shell-session abstraction inside the sandbox, with each instance representing one independent shell session. It exposes cross-platform interfaces for command execution, filesystem operations, HTTP requests, and streaming I/O. Multiple chronus instances can run concurrently within the same sandbox. Together, aether and chronus allow libdsec to expose a unified interface for container and VM sandbox operations.

**CN:**
Chronus。chronus 在 sandbox 内部提供 shell 会话抽象，每个实例代表一个独立的 shell 会话。它对外提供跨平台接口，涵盖命令执行、文件系统操作、HTTP 请求与流式 I/O。同一个 sandbox 内可以并发运行多个 chronus 实例。aether 与 chronus 合在一起，使 libdsec 能够为 container 与 VM 沙箱的操作提供统一接口。

**EN:**
Base image and workspace storage. The sandbox runtime uses 3FS as a shared backing store for base images and workspace images. Container images are converted offline from OCI into EROFS, which separates metadata from data so that metadata is kept local while image data remains in 3FS. MicroVM disk images use an OverlayBD (Li et al., 2020) format over the same storage. Together, these image formats support on-demand loading and incremental snapshots over a shared base, allowing an edge to start a sandbox without first pulling a full image. §4 characterizes the workload pressures that make scalable image distribution necessary, while §5.3 describes the corresponding on-demand loading mechanism.

**CN:**
Base image 与 workspace 存储。sandbox runtime 用 3FS 作为 base image 与 workspace image 的共享后备存储。container 镜像在离线阶段从 OCI 转换为 EROFS，该格式将元数据与数据分离，因此元数据保留在本地，而镜像数据仍放在 3FS 中。microVM 磁盘镜像则在同一存储之上采用 OverlayBD（Li et al., 2020）格式。这些镜像格式共同支持按需加载以及基于共享 base 的增量快照，使 edge 无需先拉取完整镜像即可启动 sandbox。§4 刻画了使可扩展镜像分发成为必要的工作负载压力，§5.3 则描述相应的按需加载机制。

### 3.4. Cloud Bursting with Selective Offloading

**EN:**
DSec uses cloud VMs to absorb transient peaks in sandbox demand while serving the steady-state workload on-premise. When on-premise utilization exceeds 80%, the placement engine offloads a portion of eligible incoming sandbox creation requests to cloud VMs.

**CN:**
DSec 用云端 VM 吸收 sandbox 需求的瞬时峰值，同时把稳态负载留在本地（on-premise）承担。当本地利用率超过 80% 时，placement engine 会把一部分符合条件的入站 sandbox 创建请求卸载到云端 VM。

**EN:**
Instead of combining a managed container service with object storage, we reuse the on-premise container runtime and EROFS-based image-loading path on cloud VMs. The EROFS images reside in a cloud-hosted distributed filesystem and are mounted by the cloud VMs. Production file-access traces show that a compact, de-duplicated EROFS image set totaling 30 TB covers the image files accessed by 70% of container tasks. We synchronize this shared image set to the cloud filesystem offline. Container tasks whose image dependencies are fully contained in this set are classified as cloud-eligible. Other tasks remain on-premise. In production, 200 cloud VMs in one scale unit absorb ∼30% of peak overflow, increasing capacity without over-provisioning the on-premise cluster.

**CN:**
我们没有采用"托管容器服务 + 对象存储"的组合，而是在云端 VM 上复用了本地已有的 container runtime 与基于 EROFS 的镜像加载路径。EROFS 镜像存放在云端托管的分布式文件系统中，由云端 VM 挂载。生产环境的文件访问 trace 显示，一套紧凑、去重后总计 30 TB 的 EROFS 镜像集合，覆盖了 70% 的 container 任务所访问的镜像文件。我们离线地把这套共享镜像集合同步到云端文件系统。镜像依赖完全落在该集合内的 container 任务被判定为 cloud-eligible，其余任务仍留在本地。在生产中，一个 scale unit 内的 200 台云端 VM 可吸收约 30% 的峰值溢出，从而在不使本地集群过度配置的前提下提升容量。

## 4. Production Sandbox Workloads and Platform Challenges

**EN:**
This chapter characterizes the production workloads served by DSec and the platform challenges that follow from them. We report measurements only for containers and microVMs, which together account for most sandbox instances and resource consumption in production. The measurements show a combination that is unusual for conventional execution services: requests arrive in large bursts, each sandbox retains state across an extended interaction, CPU demand is sparse even when many sandboxes are live, and the environment working set is too diverse for node-local image caches. We connect each workload property to its system consequence here and defer the corresponding mechanisms to the following chapters.

**CN:**
本章刻画 DSec 所承载的生产负载，以及由这些负载衍生出的平台挑战。我们只报告 container 与 microVM 的测量结果，二者合计占生产环境中大多数 sandbox 实例与资源消耗。这些测量呈现出一组对常规执行服务而言并不常见的组合：请求以大规模突发方式到达；每个 sandbox 在长时间交互过程中持续保留状态；即使大量 sandbox 同时存活，CPU 需求依然稀疏；而环境工作集过于多样，节点本地镜像缓存无法承载。此处我们把每条负载特性与其系统后果对应起来，相应的机制留待后续章节讨论。

### 4.1. Lifecycle and Bursty Demand

> 图 2：每个任务所创建的 sandbox 数量分布（CDF，采样一周）：container 为 p50 = 2,528 / p90 = 7,969 / p99 = 16,388，microVM 为 p50 = 352 / p90 = 1,835 / p99 = 4,044。

**EN:**
Rollout and evaluation tasks create sandboxes in batches rather than at a steady rate. Fig. 2 shows that a typical container task already creates thousands of sandboxes, and the tail reaches tens of thousands. The largest production jobs can request up to 32K sandboxes. These requests arrive within a short window because the training or evaluation batch cannot use an instance until its environment is ready. Consequently, placement, sandbox creation, and environment setup must absorb sharp bursts, while stragglers in any stage delay useful model interaction.

**CN:**
Rollout 与评估任务以批量方式创建 sandbox，而非以平稳速率创建。图 2 显示，一个典型的 container 任务就已经创建数千个 sandbox，长尾则达到数万个。最大的生产作业可请求多达 32K 个 sandbox。这些请求在很短的窗口内集中到达，因为训练或评估批次必须等到实例环境就绪后才能使用该实例。因此，放置（placement）、sandbox 创建与环境准备都必须吸收剧烈突发，而任一阶段出现的 straggler 都会延迟有效的模型交互。

> 图 3：一个代表性 sandbox 的执行过程，由 setup、tool-call、test 三个阶段构成；setup 之后 CPU 需求呈间歇性尖峰，而内存占用与累积状态持续保留。

**EN:**
Once created, a sandbox proceeds through three broad phases, as illustrated in Fig. 3. The setup phase prepares task dependencies, tools, and initialization state. During the tool-call phase, the model alternates between output generation and sandbox operations, producing short CPU bursts separated by periods in which the sandbox waits for the next action. The test phase verifies the result and can briefly increase resource demand again. These phases do not have fixed durations, but their different resource profiles are important: setup cost is multiplied by burst size, whereas later phases retain sandbox state despite intermittent CPU activity.

**CN:**
一旦创建，sandbox 便经历三个大致划分的阶段，如图 3 所示。setup 阶段准备任务依赖、工具与初始化状态。在 tool-call 阶段，模型在输出生成与 sandbox 操作之间交替，产生短促的 CPU 突发，其间 sandbox 处于等待下一个动作的空闲期。test 阶段验证结果，并可能再次短暂抬高资源需求。这些阶段没有固定时长，但它们彼此不同的资源画像非常重要：setup 成本会随突发规模成倍放大，而后面的阶段则在 CPU 活动间歇的同时持续保留 sandbox 状态。

**EN:**
The first challenge is a costly setup phase driven by composing each sandbox from independently evolving software components. For memory, microVMs incur two sources of waste. 在内存方面，microVM 存在两个浪费来源。第一，经由虚拟块设备读取的镜像数据可能先被宿主机缓存一次，又被每个 guest 再缓存一次，导致同一份数据在 guest 与宿主机的边界上被重复缓存。第二，guest 内部的空闲页在没有显式上报的情况下不会被归还给宿主机。由于申请的内存容量常常超过实际需求，guest 内部几乎没有压力去回收非活跃页。图 7 还显示这些 sandbox 生命周期很长：container 的生命周期中位数为 17.4 分钟，microVM 为 15.5 分钟，而两种后端的 p99 生命周期都超过三小时。这种长生命周期放大了被占用内存的代价。综合来看，这些效应限制了 microVM 的内存 overcommit，在高 sandbox 密度下尤为明显。

**EN:**
For CPU, some tasks impose strict per-step latency budgets, such as game-playing agents with a fixed time limit per move. The platform must improve CPU utilization through overcommit without interfering with latency-sensitive tasks.

**CN:**
在 CPU 方面，某些任务对每步延迟有严格预算，例如每步走子有固定时限的博弈类 agent。当 best-effort 任务与延迟敏感任务运行在互为 sibling 的同时多线程（SMT）上下文上、并且仍然共享核心执行资源时，仅把 best-effort 工作降到更低的调度优先级并不够。平台必须在通过 overcommit 提升 CPU 利用率的同时，不干扰延迟敏感任务。

**EN:**

First, bursty creation and independently evolving environment components require a setup path whose cost does not scale with repeated per-sandbox extraction. ### 5.1. Composable Environment Layers

**EN:**
Our insight is that the base OS environment, each workspace, and each toolkit are logically independent layers with their own lifecycles, rather than components that must be fused into a single monolithic image. As illustrated in Fig. 4b, a toolkit can therefore be updated independently and recombined with existing base-image and workspace layers. Overlayfs natively provides the merge semantics we need: when multiple read-only lower directories are stacked, the kernel presents a unified directory tree where files from all layers coexist, resolving conflicts by priority order. A writable upper directory sits atop the stack, transparently absorbing any runtime writes without modifying the read-only layers underneath.

**CN:**
我们的洞察是：基础 OS 环境、每个 workspace 以及每个 toolkit 都是逻辑上独立的层，各自拥有自己的生命周期，而不是必须熔合进单个单体镜像的组件。如图 4b 所示，因此一个 toolkit 可以独立更新，并与已有的 base image 层和 workspace 层重新组合。Overlayfs 原生提供了我们所需的合并语义：当多个只读 lowerdir 叠加时，内核呈现一棵统一的目录树，各层的文件共存其中，并按优先级顺序解决冲突。一个可写的 upper layer 位于栈顶，透明地吸收所有运行时写入，而不修改其下方的只读层。

**EN:**
We modify the container runtime (i.e., dockerd) to dynamically compose the overlayfs stack (i.e., lowerdir) at sandbox creation time. The base image sits at the bottom, the requested workspace is inserted as a read-only layer above it, and each requested toolkit is stacked on top. This merges workspace and toolkit files into the base-image tree rather than replacing paths, directs runtime writes to the writable upper layer, and permits arbitrary layer combinations without coupling their lifecycles. Consequently, upgrading 𝑚 base images now requires rebuilding only those 𝑚 base layers, leaving workspaces and toolkits untouched, while upgrading 𝑘 toolkits requires rebuilding only those 𝑘 toolkit layers. This reduces the 𝑂(𝑚·𝑁) and 𝑂(𝑘·𝑁) costs of the monolithic-image scheme to 𝑂(𝑚) and 𝑂(𝑘).

**CN:**
我们修改了容器运行时（即 dockerd），使其在 sandbox 创建时动态组装 overlayfs 栈（即 lowerdir）。base image 位于最底部，被请求的 workspace 作为只读层插入其上，每个被请求的 toolkit 再层层叠在其上。这样就把 workspace 与 toolkit 的文件合并进 base image 的目录树，而不是替换其中的路径；运行时写入被导向可写的 upper layer；并且允许任意层组合而不将其生命周期耦合在一起。因此，升级 𝑚 个 base image 现在只需重建这 𝑚 个 base 层，workspace 与 toolkit 不受影响；而升级 𝑘 个 toolkit 只需重建这 𝑘 个 toolkit 层。这把单体镜像方案中的 𝑂(𝑚·𝑁) 与 𝑂(𝑘·𝑁) 成本降为 𝑂(𝑚) 与 𝑂(𝑘)。

**EN:**
Since published environment layers are immutable, we store them in EROFS (Gao et al., 2019), a filesystem designed specifically for read-only data. Compared with writable filesystems such as ext4 or XFS, EROFS avoids write-related bookkeeping and uses a simpler, more compact on-disk layout. EROFS also supports data compression while preserving random access to file contents. Unlike a tar.gz archive, EROFS can read and decompress only the compressed blocks covering the requested data, so the complete image does not have to be transferred and unpacked before use.

**CN:**
由于已发布的环境层是不可变的，我们把它们存放在 EROFS (Gao et al., 2019) 中——一种专为只读数据设计的文件系统。与 ext4 或 XFS 这类可写文件系统相比，EROFS 省去了与写操作相关的记账开销，并使用更简单、更紧凑的磁盘布局。EROFS 还支持数据压缩，同时保留对文件内容的随机访问。与 tar.gz 归档不同，EROFS 只读取并解压覆盖所请求数据的那部分压缩块，因此完整镜像不必在使用前先被传输和解包。

**EN:**
For microVMs, base images and toolkits are packaged as independently versioned EROFS images and exposed to the guest as read-only block devices. Inside the guest, the root filesystem uses overlayfs, with the mounted EROFS filesystems as lower layers and a directory on an ext4-formatted writable disk as the upper layer. This gives microVMs the same composable-layer model as containers.

**CN:**
对于 microVM，base image 与 toolkit 被打包为各自独立版本化的 EROFS 镜像，并以只读块设备的形式暴露给 guest。在 guest 内部，根文件系统使用 overlayfs，把已挂载的 EROFS 文件系统作为 lower layer，把 ext4 格式可写磁盘上的一个目录作为 upper layer。这使 microVM 获得与容器相同的组合层模型。

### 5.2. High-Density Resource Management

#### Memory efficiency

**EN:**
Virtio-pmem with DAX (QEMU Project, 2026) eliminates page-cache duplication by mapping file accesses directly to host-backed pages without copying them into guest RAM, allowing co-located microVMs to share one host page-cache copy (§8.4). However, virtio-pmem is not suitable for every disk. First, cold accesses through virtio-pmem with DAX can require synchronous fault handling to establish mappings and make backing data available. The buffered virtio-blk path can instead benefit from guest-side readahead and batched block I/O. Second, the guest must allocate struct page metadata for the entire pmem-backed address range. With 4 KiB pages and a 64-byte struct page, this metadata requires guest RAM equal to 1/64 of the pmem device capacity. For example, a 128 GB pmem device requires 2 GB of guest RAM for this metadata.

**CN:**
带 DAX 的 virtio-pmem (QEMU Project, 2026) 把文件访问直接映射到 host 侧的后备页，而不将其拷贝进 guest RAM，从而消除了 page cache 的重复，使同机共置的多个 microVM 共享同一份 host page cache（§8.4）。然而，virtio-pmem 并不适用于所有磁盘。第一，通过带 DAX 的 virtio-pmem 进行的冷访问可能需要同步的缺页处理，以建立映射并使后备数据可用；而带缓冲的 virtio-blk 路径反而可以利用 guest 侧的预读与批量块 I/O。第二，guest 必须为整个由 pmem 支撑的地址范围分配 struct page 元数据。以 4 KiB 页与 64 字节的 struct page 计，这部分元数据需要相当于 pmem 设备容量 1/64 的 guest RAM。例如，一块 128 GB 的 pmem 设备需要 2 GB 的 guest RAM 来存放这些元数据。

**EN:**
For disks that do not use virtio-pmem, cold file data can accumulate in the guest page cache and must be reclaimed separately. We therefore combine DAMON (Data Access MONitor) (Park et al., 2019) with virtio-balloon free-page reporting. The virtio-balloon driver (Waldspurger, 2002) supports free-page reporting: the guest periodically scans its buddy allocator and proactively reports free pages to the host hypervisor, which releases the corresponding host memory via madvise(MADV_DONTNEED). By default, free-page reporting operates on order-9 pages, corresponding to 2 MiB regions with 4 KiB base pages, although this order can be adjusted through a kernel parameter. To boost free-page reporting, we employ DAMON, a sampling-based memory-access monitoring framework in Linux. DAMON periodically samples page-access bits to identify cold file pages that have remained untouched beyond a configurable age threshold and evicts them through the kernel’s reclaim path. This reclamation frees scattered file pages back to the buddy allocator, which coalesces them into higher-order blocks that satisfy the requirement of free-page reporting.

**CN:**
对于不使用 virtio-pmem 的磁盘，冷的文件数据会积累在 guest page cache 中，必须被单独回收。因此我们把 DAMON（Data Access MONitor）(Park et al., 2019) 与 virtio-balloon 的 free-page reporting (FPR) 结合起来。virtio-balloon 驱动 (Waldspurger, 2002) 支持 free-page reporting：guest 周期性扫描其 buddy allocator，主动把空闲页上报给 host hypervisor，后者通过 madvise(MADV_DONTNEED) 释放相应的 host 内存。默认情况下，free-page reporting 以 order-9 页为单位工作，在 4 KiB 基础页下对应 2 MiB 区域，不过该 order 可通过内核参数调整。为增强 free-page reporting 的效果，我们引入了 DAMON——Linux 中一个基于采样的内存访问监控框架。DAMON 周期性采样页访问位，识别出超过可配置年龄阈值仍未被触碰的冷文件页，并通过内核的回收路径将其逐出。这次回收把零散的文件页归还给 buddy allocator，后者将它们合并为更高阶的块，从而满足 free-page reporting 的要求。

**EN:**
In our evaluation in §8.4, DAMON with balloon free-page reporting reduces memory consumption by 21.2% without significant CPU overhead. In production, we enable virtio-pmem with DAX for the read-only EROFS base-image and toolkit layers, while using DAMON with balloon free-page reporting to reclaim memory for larger writable disks.

**CN:**
在 §8.4 的评测中，DAMON 配合 balloon free-page reporting 将内存占用降低了 21.2%，且没有显著的 CPU 开销。在生产环境中，我们对只读的 EROFS base image 层与 toolkit 层启用带 DAX 的 virtio-pmem，而对较大的可写磁盘使用 DAMON 配合 balloon free-page reporting 来回收内存。

#### QoS-aware CPU scheduling

**EN:**
To eliminate SMT-level CPU interference, DSec classifies sandboxes into latency-sensitive (LS) and best-effort (BE) classes. BE sandboxes are placed under SCHED_IDLE so that they yield the CPU whenever an LS task is runnable. Because scheduler priority alone does not prevent interference between sibling hardware threads, we also enable Linux core scheduling (Zijlstra et al., 2021) for LS sandboxes, preventing unrelated BE work from running on the sibling thread of the same physical core. This two-layer policy preserves LS per-step latency budgets while still allowing BE tasks to use idle cycles, reducing SMT-induced latency inflation from 45.2% to 17.3%, as detailed in §8.5.

**CN:**
为消除 SMT 层面的 CPU 干扰，DSec 把 sandbox 划分为延迟敏感（LS）与尽力而为（BE）两类。BE sandbox 被置于 SCHED_IDLE 之下，从而只要有 LS 任务可运行就让出 CPU。仅靠调度优先级并不能阻止兄弟硬件线程之间的相互干扰，因此我们还为 LS sandbox 启用 Linux core scheduling (Zijlstra et al., 2021)，阻止无关的 BE 工作在同一物理核的兄弟线程上运行。这一两层策略在保住 LS 每步延迟预算的同时，仍允许 BE 任务利用空闲周期，把 SMT 引起的延迟膨胀从 45.2% 降到 17.3%，详见 §8.5。

### 5.3. Scalable Image Distribution and On-Demand Loading

**EN:**
The key observation is that sandboxes typically access only a small fraction of their image data, as illustrated by the samples in Tab. 3. On-demand pulling therefore addresses not just the timing problem but the volume problem: total I/O shrinks in proportion to the fraction actually used rather than merely being moved to a different phase.

**CN:**
关键观察是：sandbox 通常只访问其镜像数据的一小部分，如表 3 中的样本所示。因此按需拉取不仅解决时间问题，也解决体量问题：总 I/O 随实际使用的比例成比例缩小，而不只是被挪到另一个阶段。

**EN:**
Existing on-demand image distribution systems often combine a container registry with peer-to-peer delivery to prevent the registry from becoming a bottleneck (Wang et al., 2021). We instead host images on 3FS, which already supports our production training workloads at scale. This choice reuses the existing storage infrastructure and avoids deploying a separate image-distribution layer. However, 3FS exhibits highly asymmetric I/O characteristics: it sustains high throughput for large sequential reads and writes but performs poorly on small random I/O. This asymmetry dictates our design:

1. Writes stay local. Sandbox writes are irregular and uncontrollable, including small and frequent writes such as log files. We place the writable layer on the node’s local disk, avoiding the small-write penalty of 3FS entirely.
2. Reads are on-demand and bulk. Read-only image data is fetched from 3FS only when accessed, and the I/O is performed in bulk to exploit 3FS’s high throughput for large I/O requests.
3. Metadata is preferably kept local. Filesystem metadata is often accessed through small reads. When the image format permits, we separate metadata from data and prefetch the metadata to the local node.

**CN:**
现有的按需镜像分发系统常常把容器 registry 与点对点分发结合起来，以避免 registry 成为瓶颈 (Wang et al., 2021)。我们改为把镜像托管在 3FS 上，它已经在大规模上支撑我们的生产训练负载。这一选择复用了现有存储基础设施，避免了额外部署一套镜像分发层。然而，3FS 的 I/O 特性高度不对称：它对大的顺序读写能维持高吞吐，但在小的随机 I/O 上表现很差。这种不对称决定了我们的设计：

1. 写入留在本地。Sandbox 的写入不规则且不可控，包含诸如日志文件的小而频繁的写入。我们把可写层放在节点本地磁盘上，从而完全避开 3FS 的小写惩罚。
2. 读取按需且批量。只读镜像数据仅在被访问时才从 3FS 取回，并且 I/O 以批量方式执行，以利用 3FS 在大 I/O 请求上的高吞吐。
3. 元数据尽量保存在本地。文件系统元数据常常通过小读访问。当镜像格式允许时，我们把元数据与数据分离，并把元数据预取到本地节点。

**EN:**
For containers, EROFS helps realize these design principles. First, since EROFS is strictly read-only, all runtime writes land in the overlayfs upper directory on local storage. Second, EROFS serves file content through buffered I/O on demand, while kernel readahead coalesces adjacent blocks into larger requests. Third, EROFS provides a multi-device mode that separates filesystem metadata from file data. Nydus (Dragonfly Community, 2020) adopts a related design: its EROFS-compatible format separates filesystem metadata from data blobs and supports lazy loading, with file data fetched on demand from a registry or object store through a userspace backend (e.g., fscache/FUSE). We instead download the EROFS metadata to the worker’s local disk while leaving file data on 3FS, so metadata traversal and pathname lookup do not incur remote I/O. This separates the write path (local and small-I/O friendly) from the read path (remote, on-demand, and bulk), matching the asymmetric performance profile of 3FS.

**CN:**
对容器而言，EROFS 帮助实现了这些设计原则。第一，由于 EROFS 严格只读，所有运行时写入都落在本地存储上的 overlayfs upper 目录。第二，EROFS 以缓冲 I/O 的方式按需提供文件内容，同时内核预读会把相邻块合并为更大的请求。第三，EROFS 提供 multi-device 模式，可把文件系统元数据与文件数据分离。Nydus (Dragonfly Community, 2020) 采用了相关设计：其兼容 EROFS 的格式把文件系统元数据与数据 blob 分离，并支持懒加载，文件数据经由用户态后端（例如 fscache/FUSE）从 registry 或对象存储按需取回。我们改为把 EROFS 元数据下载到 worker 本地磁盘，而把文件数据留在 3FS 上，这样元数据遍历与路径名查找就不会产生远程 I/O。这把写路径（本地、对小 I/O 友好）与读路径（远程、按需、批量）分开，与 3FS 的不对称性能特征相匹配。

**EN:**
Although this design avoids full-image pulling, mounting a large number of EROFS layers can still add overhead to container creation. We therefore collapse consecutive layers within a size threshold (e.g., 3 GB) offline into a single pair of EROFS images for metadata and data, while preserving overlayfs whiteout semantics to represent file deletions correctly. This reduces the final mount count, avoids excessive file duplication, and preserves page-cache reuse across images that share common layers. We also use EROFS file-backed mount mode to eliminate the loop-device block-mapping layer and its overhead.

**CN:**
尽管这一设计避免了全镜像拉取，挂载大量 EROFS 层仍会给容器创建带来额外开销。因此我们在离线阶段把尺寸阈值以内（例如 3 GB）的连续层折叠为元数据与数据各一份的单个 EROFS 镜像对，同时保留 overlayfs 的 whiteout 语义以正确表示文件删除。这降低了最终的挂载数量，避免过度的文件重复，并保留跨共享公共层的镜像之间的 page cache 复用。我们还使用 EROFS 的 file-backed mount 模式，以消除 loop device 的块映射层及其开销。

**EN:**
The container-style EROFS/overlayfs stack does not meet all microVM filesystem compatibility requirements. For example, Docker’s overlay2 driver cannot use an overlayfs-backed data directory. An alternative would be to export the host-mounted filesystem to the guest via virtio-fs, but our Firecracker backend does not support this interface (Agache et al., 2020). The microVM storage design is therefore not identical to the container design. Read-only base-image and toolkit layers still use EROFS, while OverlayBD serves writable ext4 disks, including a separate disk mounted directly at Docker’s data root for Docker-in-microVM workloads.

**CN:**
容器式的 EROFS/overlayfs 栈并不能满足 microVM 文件系统的全部兼容性要求。例如，Docker 的 overlay2 驱动无法使用由 overlayfs 支撑的数据目录。另一种做法是通过 virtio-fs 把 host 侧已挂载的文件系统导出给 guest，但我们的 Firecracker 后端不支持该接口 (Agache et al., 2020)。因此 microVM 的存储设计与容器设计并不完全相同。只读的 base image 层与 toolkit 层仍使用 EROFS，而由 OverlayBD 提供可写 ext4 磁盘，其中包括一块直接挂载在 Docker data root 上的独立磁盘，用于 Docker-in-microVM 类型的负载。

**EN:**
We expose the OverlayBD-backed disks through ublk, a userspace block-device framework. This block-level path provides on-demand reads and local writes, and supports incremental disk snapshots without repacking modified files into EROFS. Unlike the multi-device EROFS path, ext4 metadata remains embedded in the block image, so metadata reads can trigger remote I/O. Our ublk implementation mitigates these small reads by fetching OverlayBD data in 256 KiB chunks and storing it in a second-level local filesystem cache. Even after a chunk is evicted from the page cache, it remains available in the local cache and does not need to be fetched from 3FS again. Both paths keep writes local and minimize small I/O requests to 3FS.

**CN:**
我们通过 ublk——一个用户态块设备框架——来暴露由 OverlayBD 支撑的磁盘。这条块级路径提供按需读与本地写，并支持增量磁盘快照，而无需把被修改的文件重新打包进 EROFS。与 multi-device EROFS 路径不同，ext4 的元数据仍内嵌在块镜像中，因此元数据读可能触发远程 I/O。我们的 ublk 实现以 256 KiB 为单位取回 OverlayBD 数据，并把它存放在二级的本地文件系统缓存中，以此缓解这些小读。即使某个数据块已从 page cache 中被逐出，它仍可在本地缓存中使用，无需再次从 3FS 取回。两条路径都把写入保留在本地，并尽量把发往 3FS 的小 I/O 请求降到最低。

## 6. Co-design with the RL framework

**EN:**
DSec serves all sandbox workloads used in the RL training and evaluation from DeepSeek V3.2 (DeepSeek-AI, 2025) to V4.1 (DeepSeek-AI, 2026). Beyond efficient sandbox execution, supporting these workloads requires coordination with the RL framework on execution lifecycle and security policy. This section first describes scalable construction of agent environments (§6.1). It then explains how agent loop containers decouple rollout execution from GPU training jobs (§6.2) and how pause/resume coordinates resource reclamation with training preemption (§6.3). Finally, it examines agent behaviors that compromise task integrity or disrupt execution environments (§6.4), followed by the access controls used to mitigate these risks (§6.5).

**CN:**
从 DeepSeek V3.2 (DeepSeek-AI, 2025) 到 V4.1 (DeepSeek-AI, 2026)，RL 训练与评测中所用的全部 sandbox 负载都由 DSec 承载。除了高效的 sandbox 执行之外，支撑这些负载还要求与 RL 框架在执行生命周期和安全策略上协同。本节首先描述 agent 环境的可扩展构建（§6.1）。随后说明 agent loop 容器如何把 rollout 执行与 GPU 训练作业解耦（§6.2），以及 pause/resume 如何把资源回收与训练抢占协调起来（§6.3）。最后，考察损害任务完整性或破坏执行环境的 agent 行为（§6.4），以及随后用于缓解这些风险的访问控制（§6.5）。

### 6.1. Build environments of Agents, by Agents, for Agents

**EN:**
Manually constructing the large number of environments required by agentic RL is impractical. Instead, we let agents build environments interactively on the same infrastructure used for training and evaluation. DSec supports this workflow by pack_diff: at any point, an agent can checkpoint a sandbox by taking an incremental disk snapshot, which can later be restored as a new sandbox. This checkpoint-and-restore interface turns an interactive session directly into a reusable environment, allowing environments to be built, validated, and consumed on the same infrastructure without a separate image-building pipeline.

**CN:**
人工构建 agentic RL 所需的大量环境并不现实。作为替代，我们让 agent 在训练与评测所用的同一套基础设施上交互式地构建环境。DSec 通过 pack_diff 支撑这一流程：agent 在任何时刻都可以对 sandbox 做一次增量磁盘快照来建立 checkpoint，该快照随后可被恢复为一个新的 sandbox。这一 checkpoint-and-restore 接口把一次交互式会话直接变成一个可复用的环境，使环境能够在同一套基础设施上被构建、验证与消费，而无需一条独立的镜像构建流水线。

**EN:**
We maintain an internal set of rules that packed environments must adhere to in order to limit their runtime performance impact on the shared infrastructure. These constraints are provided as instructions to the agents that build environments. To track all environments and keep pace with the evolving infrastructure, our researchers also built an internal platform that quality-checks agent-built environments and exports them in standardized formats for consumption by RL and evaluation tasks.

**CN:**
我们维护了一套内部规则，被封装（packed）的环境必须遵守，以限制其运行时对共享基础设施的性能影响。这些约束以指令形式提供给构建环境的 agent。为了追踪所有环境并跟上基础设施的演进，我们的研究人员还搭建了一个内部平台，对 agent 构建的环境做质量检查，并以标准化格式导出，供 RL 与评测任务消费。

**EN:**
Because environments are built and consumed on the same sandbox infrastructure, preventing information leakage between the two stages is important. Builders and runtime agents use separate accounts, and build-time residual data is removed from the writable layer before packing so that reference answers are not carried into the resulting image.

**CN:**
由于环境是在同一套 sandbox 基础设施上被构建和消费的，防止两个阶段之间的信息泄漏很重要。构建者与运行时 agent 使用不同账号，并且在打包前从可写层中清除构建期残留数据，以免参考答案被带进最终镜像。

### 6.2. Separate agent loop from the RL framework

**EN:**
Training jobs in our GPU cluster are routinely preempted to improve utilization. For long-running agentic rollouts, coupling rollout execution to the training job makes preemption particularly costly: the agent loop may be terminated after substantial progress, even though the corresponding sandbox state remains intact. To resume such rollouts, the system must preserve both the agent’s execution state and the sandbox state.

**CN:**
为提升利用率，我们 GPU 集群中的训练作业经常被抢占。对于长时间的 agentic rollout，把 rollout 执行与训练作业耦合在一起会让抢占的代价尤为高昂：agent loop 可能在大幅推进之后被终止，尽管对应的 sandbox 状态仍然完好。要恢复这类 rollout，系统必须同时保住 agent 的执行状态与 sandbox 状态。

**EN:**
In earlier versions of the training pipeline, the agent loop ran inside the preemptible GPU training pod together with the model-serving and RL framework. When the GPU job was preempted, the agent loop was lost while the sandbox persisted. Recovery therefore relied on a command log to reconcile the rollout state restored by the training framework with the sandbox’s execution state. During replay, completed operations reused recorded results rather than being re-executed, avoiding duplicate side effects from non-idempotent commands.

**CN:**
在训练流水线的早期版本中，agent loop 与被抢占的 GPU 训练 pod 以及模型服务、RL 框架一起运行在该 pod 内。当 GPU 作业被抢占时，agent loop 随之丢失，而 sandbox 却仍然存活。因此恢复只能依赖一份命令日志，把训练框架恢复出的 rollout 状态与 sandbox 的执行状态对齐。重放过程中，已完成的操作直接复用记录下来的结果而不再重新执行，从而避免了非幂等命令带来的重复副作用。

**EN:**
Starting with DeepSeek-V4.1 (DeepSeek-AI, 2026), we instead move rollout execution onto DSec and separate it into two components: an agent sandbox, which hosts the scaffold (e.g., DeepSeek Harness) and its tools, and a worker container, which manages the sandbox and provides a scaffold-agnostic control layer for the rollout. Both components run outside the preemptible GPU pool. This design decouples rollout lifetime from trainer lifetime. The worker container and agent sandbox jointly retain the complete rollout state and act as its single source of truth, allowing a preempted GPU job to reconnect and continue without reconstructing execution through command-log replay. This removes rollout-state recovery logic from the RL framework, reduces cross-component coordination, and simplifies failure handling.

**CN:**
从 DeepSeek-V4.1 (DeepSeek-AI, 2026) 起，我们改为把 rollout 执行移到 DSec 上，并将其拆分为两个组件：agent sandbox，承载 scaffold（例如 DeepSeek Harness）及其工具；以及 worker container，负责管理该 sandbox 并提供与 scaffold 无关的 rollout 控制层。两个组件都运行在可抢占的 GPU 资源池之外。这一设计把 rollout 的生命周期与 trainer 的生命周期解耦。worker container 与 agent sandbox 共同保有完整的 rollout 状态，并作为其唯一事实来源，使被抢占的 GPU 作业可以重新连接并继续，而无需通过命令日志重放来重建执行过程。这从 RL 框架中去掉了 rollout 状态恢复逻辑，减少了跨组件协调，并简化了故障处理。

### 6.3. Suspending Sandboxes for Preemptive RL Training

**EN:**
Because GPU-job preemption is inevitable (§6.2), sandbox state must remain on DSec until the rollout completes. However, this can leave many idle sandboxes consuming memory while training is suspended. The RL framework therefore proactively sends pause requests to all sandboxes associated with a preempted job, allowing DSec to reclaim memory while preserving their execution state. For both containers and microVMs, any subsequent request to a paused sandbox transparently resumes it before executing the requested operation.

**CN:**
由于 GPU 作业被抢占不可避免（§6.2），sandbox 状态必须留在 DSec 上直到 rollout 完成。然而，在训练被挂起期间，这会让许多空闲 sandbox 持续占用内存。因此 RL 框架会主动向与被抢占作业相关联的所有 sandbox 发送 pause 请求，使 DSec 能够在保住其执行状态的前提下回收内存。对容器与 microVM 而言，此后任何发往已暂停 sandbox 的请求，都会在执行所请求的操作之前透明地将其恢复。

**EN:**
**Containers.** The edge first issues docker pause to freeze the container’s process tree. It then enables swapping through the container’s memory.swap.max setting and triggers proactive memory reclamation through memory.reclaim. This reclaims memory from both anonymous and file-backed pages while preserving the container’s execution state. To resume a container, the edge applies MADV_WILLNEED to its processes’ memory mappings to initiate asynchronous prefetching, then issues docker unpause to resume execution.

**CN:**
**Containers。** edge 先发出 docker pause 以冻结该容器的进程树，然后通过容器的 memory.swap.max 设置启用 swap，并通过 memory.reclaim 触发主动内存回收。这会从匿名页与文件后备页两方面回收内存，同时保住容器的执行状态。要恢复一个容器，edge 对其各进程的内存映射施加 MADV_WILLNEED 以启动异步预取，随后发出 docker unpause 恢复执行。

**EN:**
**MicroVMs.** To pause a microVM, DSec saves its memory and execution state in a snapshot, then terminates the running Firecracker process to release the microVM’s runtime memory. On resume, DSec starts a new process and restores the snapshot to continue guest execution.

**CN:**
**MicroVMs。** 要暂停一个 microVM，DSec 把其内存与执行状态保存为快照，然后终止正在运行的 Firecracker 进程以释放该 microVM 的运行时内存。恢复时，DSec 启动一个新进程并载入快照，从中继续 guest 的执行。

### 6.4. Agent Misbehavior and System Failures

**EN:**
Our production experience reveals two broad risks in agent execution. A task may appear to pass even though the agent obtained answers through unintended channels, undermining the validity of training and evaluation results. Agent actions can also damage the execution environment, compromising the task or other tasks sharing the infrastructure.

**CN:**
我们的生产经验揭示了 agent 执行中的两大类风险。其一，任务可能看似通过，但 agent 实际上是通过非预期渠道拿到了答案，从而削弱训练与评测结果的有效性。其二，agent 的行为也可能破坏执行环境，危及本任务或共享同一基础设施的其他任务。

**EN:**
**Obtaining answers through unintended channels.** Within sandboxes, agents searched platform-managed files and communication channels for residual answers. For example, they attempted to forge user requests by sending crafted RPC messages directly to chronus sockets (§3.3) and inspected chronus logs for leaked answers. Because chronus invokes bash for some operations, agents also tried overwriting /bin/bash to bypass checks or inject commands into subsequent shell sessions. After we introduced file read/write and socket access controls (§6.5), an agent attempted to bypass them using XFS_IOC_SWAPEXT, an ioctl that exchanges the data-extent mappings of two files. The goal was to make protected file contents accessible through another file descriptor. The attempt corrupted XFS metadata and forced a filesystem shutdown, illustrating how answer-seeking behavior can even disrupt infrastructure.

**CN:**
**通过非预期渠道获取答案。** 在 sandbox 内部，agent 会翻找平台托管的文件与通信渠道以寻找残留答案。例如，它们尝试直接把构造好的 RPC 消息发给 chronus 的 socket（§3.3）来伪造用户请求，并检查 chronus 日志是否有泄漏的答案。由于 chronus 对某些操作会调用 bash，agent 还尝试覆写 /bin/bash，以绕过检查或向后续 shell 会话注入命令。在我们引入文件读写与 socket 访问控制（§6.5）之后，有一个 agent 尝试用 XFS_IOC_SWAPEXT 绕过这些控制——该 ioctl 会交换两个文件的数据 extent 映射，其目的是让受保护文件的内容能通过另一个文件描述符被访问。这次尝试损坏了 XFS 元数据并迫使文件系统关闭，说明寻求答案的行为甚至可能破坏基础设施。

**EN:**
**Tampering with execution environments.** Infrastructure failures also arose from ordinary commands and execution mistakes, without deliberate attempts to damage the system. In one case, an agent recursively ran grep from the root directory, traversed /proc, and read /proc/kpagecgroup, triggering a kernel bug that crashed the kernel. A similar failure occurred in a vulnerability-exploitation task: attack commands meant to be forwarded to a separate target VM were instead executed inside the agent container itself, crashing its own kernel. Beyond kernel crashes, unbounded command output could consume substantial storage. For example, an agent invoked yes, whose continuous output was recorded by chronus so that users could retrieve command output asynchronously. The captured stdout accumulated tens of gigabytes of data on storage.

**CN:**
**篡改执行环境。** 基础设施故障也会由普通命令与执行失误引起，并非都是蓄意破坏系统。有一种情况是：agent 从根目录开始递归执行 grep，遍历 /proc 并读取 /proc/kpagecgroup，触发了一个内核 bug，导致内核崩溃。另一例类似故障出现在漏洞利用任务中：本应被转发到一台独立目标 VM 的攻击命令，却在 agent 容器自身内部执行，把它自己的内核搞崩了。除内核崩溃外，无界的命令输出还可能占用大量存储。例如，一个 agent 调用了 yes，其持续不断的输出被 chronus 记录下来，以便用户异步取回命令输出；捕获的 stdout 在存储上累积到了数十 GB。

### 6.5. Access-Control Mitigations

**EN:**
No single mechanism can prevent all agent misbehavior and system failures. We therefore strengthen observability to identify emerging problems and continuously harden DSec as models evolve. Here we describe access controls that limit agents’ ability to obtain answers through unintended channels and thereby mitigate reward hacking (Amodei et al., 2016; Skalse et al., 2022). These controls address only part of the problem and do not provide a general defense against destructive behavior such as triggering kernel bugs.

**CN:**
没有任何单一机制能阻止所有 agent 失范行为与系统故障。因此我们加强可观测性以发现新出现的问题，并随着模型演进持续加固 DSec。这里我们描述的是限制 agent 通过非预期渠道获取答案能力的访问控制，借此缓解 reward hacking (Amodei et al., 2016; Skalse et al., 2022)。这些控制只解决了问题的一部分，并不能为诸如触发内核 bug 这类破坏性行为提供通用防御。

**EN:**
**File and socket access control (AppArmor).** We use AppArmor profiles to control file read/write permissions and socket access, including access to chronus’s logs and Unix-domain sockets. These policies apply to agent-controlled processes even when they run as root inside the sandbox. They limit attempts to extract residual answers from logs or forge user requests through internal communication channels.

**CN:**
**文件与 socket 访问控制（AppArmor）。** 我们用 AppArmor profile 来控制文件读写权限与 socket 访问，包括对 chronus 日志和 Unix-domain socket 的访问。这些策略作用于 agent 控制的进程，即使它们以 root 身份在 sandbox 内运行亦然。它们限制了从日志中提取残留答案、或经由内部通信渠道伪造用户请求的尝试。

**EN:**
**Fine-grained network control (eBPF).** The training framework specifies task-specific network permissions organized by domain or mirror service. For example, List. 1 permits access to PyPI while denying access to NPM. DSec enforces the corresponding allowlists through per-sandbox eBPF programs that filter traffic by IP address, port, and protocol, rejecting traffic outside the allowlist. The policies can be updated dynamically as tasks move between stages with different connectivity requirements.

**CN:**
**细粒度网络控制（eBPF）。** 训练框架按域名或镜像服务来组织并指定任务相关的网络权限。例如，List. 1 允许访问 PyPI 而禁止访问 NPM。DSec 通过 per-sandbox 的 eBPF 程序强制执行相应的 allowlist：按 IP 地址、端口与协议过滤流量，拒绝 allowlist 之外的流量。当任务在不同连通性要求的阶段之间迁移时，这些策略可以动态更新。

## 7. Implementation

**EN:**
We highlight a few additional implementation details that proved important in practice.

**CN:**
我们着重介绍一些在实践中被证明很重要的额外实现细节。

#### Placement engine strategy

**EN:**
Extreme spikes of thousands of sandboxes in sub-seconds and heavy oversubscription require spreading incremental load evenly with elastic rather than pinned resource reservations. We tackle the problem with the following aspects. 1) We adopt a power-of-k-choices algorithm (Mitzenmacher, 2001): the scheduler samples k nodes at random and selects the least loaded, avoiding herding and reducing interference among bursty RL environments during setup and tool calls. 2) Each placement engine instance maintains a local view by overlaying its recent placements not yet reflected in periodic watcher snapshots, accounting for in-flight load without cross-instance coordination. 3) Each edge retains final admission authority: critical resource pressure triggers rejection and selection of an alternative node, keeping the fast path lightweight while preventing stale estimates from overriding local resource limits. User isolation further bounds the blast radius of resource spikes or kernel-level faults at the cost of node-level density.

**CN:**
在亚秒级时间内出现数千个 sandbox 的极端峰值，以及严重的 oversubscription，要求以弹性的、而非钉死的资源预留方式把增量负载均匀摊开。我们从以下几个方面解决该问题。1）我们采用 power-of-k-choices 算法（Mitzenmacher, 2001）：调度器随机采样 k 个节点并选择负载最低者，从而避免羊群效应（herding），并减少突发型 RL 环境在 setup 与 tool call 期间的相互干扰。2）每个 placement engine 实例维护一份本地视图：把自身尚未反映在周期性 watcher 快照中的近期放置叠加其上，从而在无需跨实例协调的情况下计入 in-flight 负载。3）每条 edge 保留最终准入权：当出现关键资源压力时触发拒绝并改选其他节点，使快路径保持轻量，同时防止陈旧估计覆盖本地资源上限。用户隔离进一步把资源尖峰或内核级故障的影响范围限制住，代价是节点级密度下降。

#### Reliable services

**EN:**
Both auxiliary and cluster-level services must remain reliable, as outages can cause agents to fail tasks, corrupting reward signals or evaluation results. For auxiliary services, such as API gateways and package mirrors, and control-plane ingress, we apply BGP-based load balancing: instances of each service announce a shared virtual IP, and upstream switches perform ECMP routing across them. When an instance's BGP session drops, switches withdraw its route and redirect traffic to remaining instances within seconds. Cluster-level services, including the placement engine, watcher, and IAM, run multiple independent instances for availability, with regular cluster resets verifying that our Infrastructure-as-Code configuration can reconstruct all cluster-level services from scratch and recover from failures without relying on accumulated manual state.

**CN:**
辅助服务与集群级服务都必须保持可靠，因为服务中断会导致 agent 任务失败，进而污染 reward 信号或评测结果。对于辅助服务（如 API gateway 与 package mirror）以及控制面入口，我们采用基于 BGP 的负载均衡：每个服务的各实例宣告同一个 virtual IP，上游交换机在其间做 ECMP 路由。当某个实例的 BGP 会话断开时，交换机会撤销其路由，并在数秒内把流量重定向到其余实例。集群级服务（包括 placement engine、watcher 与 IAM）以多个独立实例运行以保证可用性，并通过定期集群重建来验证我们的 IaC/Infrastructure-as-Code 配置能够从零重建全部集群级服务，且不依赖累积的人工状态即可从故障中恢复。

#### Dynamic lower-layer insertion in dockerd

**EN:**
We modify the open-source Docker daemon (based on the Moby project (Moby Project, 2026)) to dynamically insert EROFS-backed lower layers at container creation time. Specifically, we pass the path of a pre-mounted EROFS layer and insert it into the overlayfs stack before mounting, placing it as the topmost lower layer so it can override files in layers below. This change is minimal, requiring only 30 lines of Go code.

**CN:**
我们修改了开源 Docker daemon（基于 Moby 项目（Moby Project, 2026）），使其在容器创建时动态插入由 EROFS 支撑的 lower layer。具体而言，我们传入一个已预先挂载的 EROFS 层的路径，并在挂载前把它插入 overlayfs 栈，置于最顶部的 overlayfs lower layer，从而可以覆盖下层中的文件。该改动非常小，仅需 30 行 Go 代码。

#### Rust-based OverlayBD and ublk library

**EN:**
We use the Rust port of OverlayBD, to which we contributed, together with our Rust userspace library for ublk to form the on-demand block-storage path for Firecracker microVMs described in §5.3. The storage layer supports 3FS, object storage services such as OSS, and container registries as remote backends. It can also use the local filesystem as a second-level cache, allowing data evicted from the page cache to be served locally without another remote fetch. These storage components have been open sourced at https://github.com/kvcache-ai/AgentENV/tree/main/storage/overlaybd.

**CN:**
我们使用 OverlayBD 的 Rust 移植版（我们对该移植有贡献），配合我们自研的 Rust ublk 用户态库，构成 §5.3 所述 Firecracker microVM 的按需块存储路径。该存储层支持将 3FS、OSS 等对象存储服务以及容器镜像仓库作为远端后端。它还可以把本地文件系统用作二级缓存，使已从 page cache 中被淘汰的数据能够在本地直接提供，而无需再次远端拉取。这些存储组件已在 https://github.com/kvcache-ai/AgentENV/tree/main/storage/overlaybd 开源。

#### Memory and CPU QoS configuration

**EN:**
All mechanisms leverage existing Linux kernel features. Virtio-pmem with DAX is enabled via Firecracker device configuration and guest kernel mount options. DAMON-based reclamation is activated through guest kernel parameters and sysfs tuning. For CPU QoS, we set best-effort tasks to SCHED_IDLE and enable core scheduling via prctl(PR_SCHED_CORE) to group tasks by QoS class. No kernel modifications are required; the implementation consists entirely of configuration and integration with our sandbox orchestrator.

**CN:**
所有机制都依托现有的 Linux 内核特性。带 DAX 的 Virtio-pmem 通过 Firecracker 设备配置与 guest 内核挂载选项启用。基于 DAMON 的回收通过 guest 内核参数与 sysfs 调优激活。在 CPU QoS 方面，我们把 best-effort 任务设为 SCHED_IDLE，并通过 prctl(PR_SCHED_CORE) 启用 core scheduling，以按 QoS 类别对任务分组。无需修改内核；实现完全由配置以及与 sandbox 编排器的集成构成。

#### GPU FnCall for operator benchmarking

**EN:**
We equip FnCall with GPUs for stateless operator benchmarking. Because GPU capacity is limited, GPU FnCall uses three mechanisms to improve concurrency while preserving performance isolation. First, NVIDIA Multi-Instance GPU (MIG) partitions each GPU into isolated instances, allowing benchmarks to run concurrently with exclusive access to assigned instances. Second, CPU FnCall handles compilation and passes the resulting artifacts to GPU FnCall, avoiding unnecessary GPU occupation. Finally, a warm pool of Python processes initializes the runtime and imports libraries in advance, allowing requests to begin operator execution directly. Together, these mechanisms reduce non-GPU overhead on the execution path, thereby improving both GPU utilization and benchmarking throughput. For non-performance-sensitive tasks, we also provide a shared GPU mode that increases concurrency by allowing multiple workloads to share a GPU instance.

**CN:**
我们为 FnCall 配备 GPU，以支持无状态的 operator 基准测试。由于 GPU 容量有限，GPU FnCall 采用三种机制在保持性能隔离的同时提升并发度。第一，NVIDIA Multi-Instance GPU（MIG）把每块 GPU 切分为相互隔离的实例，使基准测试可以并发运行、且对各自分配的实例拥有独占访问。第二，由 CPU FnCall 负责编译，并把生成的产物传给 GPU FnCall，避免不必要的 GPU 占用。最后，一个 warm pool 中的 Python 进程预先初始化运行时并导入所需库，使请求可以直接开始执行 operator。这些机制共同减少了执行路径上的非 GPU 开销，从而同时提升 GPU 利用率与基准测试吞吐。对于对性能不敏感的任务，我们还提供共享 GPU 模式，允许多个工作负载共用同一个 GPU 实例以提高并发。

#### 3FS deployment

**EN:**
Each 3FS (An et al., 2024) storage server is equipped with 20 × 15 TB SSDs and 2 × 400Gbps RDMA NICs. CPU nodes access 3FS through its FUSE-based client, with EROFS metadata stored locally and file data served on demand from 3FS. Tens of storage servers support on-demand image loading for a cluster with hundreds of thousands of CPU cores.

**CN:**
每台 3FS（An et al., 2024）存储服务器配备 20 × 15 TB SSD 与 2 × 400Gbps RDMA 网卡。CPU 节点通过 3FS 基于 FUSE 的客户端访问它，其中 EROFS 元数据存放在本地，文件数据按需由 3FS 提供。数十台存储服务器即可支撑拥有数十万个 CPU 核的集群的按需镜像加载。

### 8.3 Composable Image Layers: EROFS vs Tar

**EN:**
For code repositories and development environments, we compare two approaches for provisioning the same evaluation workspace and toolkits, including task repositories, scaffold binaries, and command-line tools. The conventional approach packages these files as a compressed tar.gz archive, which is distributed and extracted into each sandbox, whereas the EROFS approach packages the same files as a compressed, read-only filesystem image that can be mounted directly as a composable layer. We replace LLM generation with a prerecorded, deterministic sequence of tool calls so that runs differ only in how their workspaces and toolkits are provisioned.

**CN:**
针对代码仓库与开发环境，我们比较两种为同一评测 workspace 与工具集（包括任务仓库、scaffold 二进制与命令行工具）提供内容的方式。传统方式把这些文件打包为压缩的 tar.gz 归档，分发后解压到每个 sandbox 中；而 EROFS 方式把同一批文件打包为压缩的只读文件系统镜像，可直接作为可组合层挂载。我们用一段预先录制、确定性的 tool call 序列替代 LLM 生成，使各次运行仅在 workspace 与工具集的提供方式上有所不同。

> 图 11：分别用逐 sandbox 解压 tar 与挂载 EROFS 层来提供评测 workspace 时，setup 阶段的 CPU 利用率与磁盘写吞吐。

**EN:**
Because tar.gz is a sequential stream format, every sandbox must decompress the archive and write all workspace and toolkit files into its local writable layer before tool calls can begin. This extends end-to-end task completion time to 79 minutes. EROFS mounts the shared layers directly without extraction, allowing sandboxes to enter the tool-call phase earlier and reducing completion time to 45 minutes, a 1.76× speedup. As shown in Fig. 11, tar-based provisioning generates roughly 5.5× the total disk-write traffic and 3.4× the peak disk-write throughput of the EROFS path. Peak CPU utilization is higher with EROFS because more sandboxes enter the tool-call phase earlier and execute operations concurrently. This does not indicate higher setup overhead, since EROFS avoids the CPU work of repeatedly decompressing and unpacking the archives. These results validate the effectiveness of the composable-layer design in §5.1.

**CN:**
由于 tar.gz 是顺序流格式，每个 sandbox 都必须解压归档并把全部 workspace 与工具集文件写入其本地可写层，之后才能开始 tool call。这把端到端任务完成时间拉长到 79 分钟。EROFS 直接挂载共享层而无需解压，使 sandbox 能更早进入 tool call 阶段，把完成时间缩短到 45 分钟，即 1.76× 的加速。如图 11 所示，基于 tar 的提供方式产生的总磁盘写流量约为 EROFS 路径的 5.5×，峰值磁盘写吞吐约为 3.4×。EROFS 的峰值 CPU 利用率更高，是因为更多 sandbox 更早进入 tool call 阶段并并发执行操作。这并不表示 setup 开销更高，因为 EROFS 避免了反复解压与展开归档的 CPU 工作。这些结果验证了 §5.1 中可组合层设计的有效性。

### 8.4 Memory under Overcommit

> 图 12：真实 agentic RL 负载下四种 Firecracker 配置的宿主机内存占用（左）与 CPU 利用率（右）；CPU 面板对前 10 分钟使用放大的时间轴，对 10–50 分钟区间使用压缩刻度。四种配置为 baseline、pmem、fpr、pmem+fpr。

**EN:**
We run a real agentic-RL workload on our test cluster and compare four Firecracker configurations: the unoptimized baseline, virtio-pmem with DAX alone, DAMON-based free-page reporting (FPR) via the virtio-balloon device alone, and both mechanisms combined. Virtio-pmem with DAX collapses the redundant per-guest page caches into a single shared host mapping, reducing peak host memory usage by 40.2% compared with baseline. DAMON + balloon FPR alone leaves peak usage largely unchanged but reduces time-integrated host memory consumption by 21.2%. Combining both mechanisms produces the lowest overall memory consumption. As Fig. 12 shows, virtio-pmem raises transient peak CPU utilization from 26.5% to 41.4%. This increase may partly reflect differences in the cold-access paths. Virtio-pmem with DAX can require synchronous fault handling to establish mappings and make backing data available, while buffered virtio-blk can benefit from guest-side readahead and batched block I/O. In CPU-constrained deployments, operators may prefer to enable FPR alone and retain virtio-blk. Together, these results validate the complementary memory optimizations in §5.2: virtio-pmem reduces page-cache duplication, while DAMON with balloon FPR reclaims idle guest memory.

**CN:**
我们在测试集群上运行真实的 agentic-RL 负载，比较四种 Firecracker 配置：未优化的 baseline、仅启用带 DAX 的 virtio-pmem、仅通过 virtio-balloon 设备启用基于 DAMON 的 free-page reporting（FPR），以及两种机制组合。带 DAX 的 virtio-pmem 将各 guest 中冗余的 page cache 折叠为单一的宿主机共享映射，相比 baseline 将宿主机峰值内存占用降低 40.2%。单独使用 DAMON + balloon FPR 时峰值占用基本不变，但将时间积分的宿主机内存消耗降低 21.2%。两种机制组合产生最低的整体内存消耗。如图 12 所示，virtio-pmem 将瞬时峰值 CPU 利用率从 26.5% 提升至 41.4%。这一上升可能部分反映了冷访问路径上的差异。带 DAX 的 virtio-pmem 可能需要同步的 fault handling 来建立映射并使后端数据可用，而带缓冲的 virtio-blk 则可以受益于 guest 侧的 readahead 与批量块 I/O。在 CPU 受限的部署中，运维者可能更倾向于仅启用 FPR 并保留 virtio-blk。综合来看，这些结果验证了 §5.2 中互补的内存优化：virtio-pmem 减少 page-cache 重复，而 DAMON 配合 balloon FPR 回收空闲的 guest 内存。

### 8.5 CPU QoS under Overcommit

**EN:**
We run latency-sensitive (LS) tasks from a real evaluation workload alongside co-located best-effort (BE) load ranging from 10% to 50% of node capacity, measuring how well our mechanism preserves per-sandbox performance under high-density deployment. We compare an unprotected baseline, SCHED_IDLE alone, and SCHED_IDLE combined with core scheduling.

**CN:**
我们运行来自真实评测负载的延迟敏感（LS）任务，同时施加占节点容量 10% 至 50% 的共置 best-effort（BE）负载，测量我们的机制在高密度部署下能在多大程度上保住每个 sandbox 的性能。我们比较三种方案：无保护的 baseline、仅 SCHED_IDLE，以及 SCHED_IDLE 与 core scheduling 组合。

> 图 13：延迟敏感 agent 在共置 best-effort CPU 负载逐步升高（10%→50%）下的每步耗时，对比无保护 baseline、仅 SCHED_IDLE、SCHED_IDLE + core scheduling；并给出无后台负载的参考线。

**EN:**
As shown in Fig. 13, we use a latency-sensitive chess application as the test workload. At 50% BE load, its per-step latency increases by 45.2% over the no-co-location baseline without QoS controls. SCHED_IDLE alone improves latency by at most 3.4% because an LS thread can still contend with BE work running on its SMT sibling. Adding core scheduling keeps latency close to the no-co-location baseline at low load and limits inflation to 17.3% at 50% load. The improvement grows as BE contention increases. These results validate the two-level CPU QoS design in §5.2: SCHED_IDLE prioritizes LS tasks, while core scheduling isolates them from BE work on sibling SMT threads. The residual degradation mainly results from reduced CPU turbo frequency under high multicore load, memory bandwidth and shared last-level cache (LLC) contention that core scheduling does not address. Since this remaining interference is already tolerable, we do not apply memory bandwidth isolation.

**CN:**
如图 13 所示，我们使用一个延迟敏感的棋类应用作为测试负载。在 50% BE 负载下，若不施加 QoS 控制，其每步延迟相对无共置 baseline 上升 45.2%。仅使用 SCHED_IDLE 最多只能把延迟改善 3.4%，因为 LS 线程仍会与运行在其 SMT 兄弟核（sibling）上的 BE 工作争抢。加入 core scheduling 后，低负载下延迟接近无共置 baseline，在 50% 负载下将膨胀限制在 17.3%。随着 BE 争用加剧，改善幅度也随之增大。这些结果验证了 §5.2 中的两级 CPU QoS 设计：SCHED_IDLE 优先调度 LS 任务，而 core scheduling 将其与兄弟 SMT 线程上的 BE 工作隔离。残余的性能退化主要来自高多核负载下 CPU turbo frequency 的下降，以及 core scheduling 无法处理的 memory bandwidth 与共享 last-level cache（LLC）争用。由于这部分残余干扰已可容忍，我们未施加 memory bandwidth 隔离。

## 9. Related Work

#### Serverless computing

**EN:**
Serverless platforms such as SAND (Akkus et al., 2018), REAP (Ustiugov et al., 2021), TrEnv (Huang et al., 2024), and RunD (Li et al., 2022) optimize cold-start latency and resource sharing for short-lived, stateless functions. These workloads typically reuse a limited set of images at high fanout, and many systems assume that the required images are already available locally. Agentic training instead uses long-lived, stateful sandboxes drawn from an image corpus that exceeds single-node storage and has low per-image fanout.

**CN:**
SAND（Akkus et al., 2018）、REAP（Ustiugov et al., 2021）、TrEnv（Huang et al., 2024）和 RunD（Li et al., 2022）等 serverless 平台针对短生命周期、无状态的函数优化 cold-start 延迟与资源共享。这类负载通常以高扇出复用一组有限的镜像，且许多系统假定所需镜像已在本地可用。而 agentic 训练使用的是长生命周期、有状态的 sandbox，其镜像库超出单节点存储容量，并且每个镜像的扇出很低。

#### LLM code execution platforms

**EN:**
Recent systems provide sandboxed code execution for LLM workflows in both training and inference. Inference-facing systems include OpenAI Code Interpreter (OpenAI, 2025), E2B (E2B, 2024), and Kimi-K2.5’s Agent Swarm (Kimi Team, 2026). Training systems such as MiMo-V2-Flash (Xiaomi LLM-Core Team, 2026) and ComputerRL (Lai et al., 2025) mention their execution environments but focus primarily on model and training design. DSec focuses on the underlying sandbox infrastructure, integrating environment composition, resource overcommit, image serving, and preemption-safe resumption within one platform.

**CN:**
近期系统为训练与推理中的 LLM 工作流提供沙箱化代码执行。面向推理的系统包括 OpenAI Code Interpreter（OpenAI, 2025）、E2B（E2B, 2024）以及 Kimi-K2.5 的 Agent Swarm（Kimi Team, 2026）。MiMo-V2-Flash（Xiaomi LLM-Core Team, 2026）和 ComputerRL（Lai et al., 2025）等训练系统提及了其执行环境，但主要关注模型与训练设计。DSec 关注底层的 sandbox 基础设施，将环境组合、资源 overcommit、镜像服务以及抢占安全恢复（preemption-safe resumption）整合到同一平台中。

#### Container image and filesystem formats

**EN:**
DADI (Li et al., 2020) and CoFS (Wang et al., 2026) support on-demand container-image loading, while FaaSNet (Wang et al., 2021) uses peer-to-peer delivery to accelerate image distribution. EROFS (Gao et al., 2019) provides a compressed read-only filesystem with random access. DSec builds on these techniques for RL training and evaluation, serving container and microVM images from 3FS rather than introducing a separate registry and peer-to-peer distribution tier.

**CN:**
DADI（Li et al., 2020）和 CoFS（Wang et al., 2026）支持按需加载容器镜像，FaaSNet（Wang et al., 2021）则利用 peer-to-peer 分发加速镜像传播。EROFS（Gao et al., 2019）提供支持随机访问的压缩只读文件系统。DSec 在 RL 训练与评测中沿用这些技术，从 3FS 提供容器与 microVM 镜像，而不是额外引入独立的 registry 与 peer-to-peer 分发层。

#### Lightweight isolation

**EN:**
To run diverse workloads, several isolation paradigms have been proposed, including microVMs (Agache et al., 2020) or VM-backed kata-containers (Kata Containers, 2017), library OSes (che Tsai et al., 2017; LiteBox, 2025), WebAssembly runtimes (Gadepalli et al., 2020; Shillaker and Pietzuch, 2020), unikernels (Cadden et al., 2020), nested kernels (Dautenhahn et al., 2015; Zhang et al., 2025), and nested virtualization (Huang et al., 2023). They offer different trade-offs among isolation, compatibility, and performance. Rather than proposing another isolation mechanism, DSec integrates multiple sandbox backends behind a unified platform, allowing callers to choose the appropriate backend for each task.

**CN:**
为运行多样化负载，已有多种隔离范式被提出，包括 microVM（Agache et al., 2020）或基于 VM 的 kata-containers（Kata Containers, 2017）、library OS（che Tsai et al., 2017; LiteBox, 2025）、WebAssembly 运行时（Gadepalli et al., 2020; Shillaker and Pietzuch, 2020）、unikernel（Cadden et al., 2020）、nested kernel（Dautenhahn et al., 2015; Zhang et al., 2025）以及 nested virtualization（Huang et al., 2023）。它们在隔离性、兼容性与性能之间给出不同的权衡。DSec 并不再提出一种新的隔离机制，而是将多种 sandbox 后端整合在统一平台之后，让调用方为每个任务选择恰当的后端。

#### RL training infrastructure

**EN:**
Systems such as Slime (Zhu et al., 2025), veRL (Sheng et al., 2025), OpenRLHF (Hu, 2026; Hu et al., 2025), and Seer (Qin et al., 2026) focus on scaling RL training through efficient GPU scheduling, communication, and sample throughput. They treat the execution environment as a black box, assuming that sandboxes are available and correctly configured. DSec operates at the complementary infrastructure layer, managing sandbox provisioning and lifecycle while coordinating execution state and security policy with the training framework.

**CN:**
Slime（Zhu et al., 2025）、veRL（Sheng et al., 2025）、OpenRLHF（Hu, 2026; Hu et al., 2025）和 Seer（Qin et al., 2026）等系统侧重通过高效的 GPU 调度、通信与样本吞吐来扩展 RL 训练。它们把执行环境视为黑箱，假定 sandbox 已可用且配置正确。DSec 工作在互补的基础设施层，负责 sandbox 的供给与生命周期管理，同时与训练框架协同执行状态与安全策略。

## 10. Conclusion

**EN:**
We presented DSec, a production sandbox platform for large-scale LLM agentic training, evaluation and environment construction. DSec exposes multiple sandbox backends through a unified interface, allowing users to select an appropriate execution environment for different functionality, compatibility, and isolation requirements. Composable EROFS-backed layers avoid repeated environment rebuilding and extraction, complementary memory sharing and reclamation mechanisms support high-density deployment, QoS-aware CPU scheduling protects latency-sensitive tasks under oversubscription, and 3FS-backed on-demand image loading reduces image distribution overhead. DSec also integrates with the RL framework for preemption-safe resumption and task-specific network policy, providing a scalable execution foundation for agentic workloads.

**CN:**
我们提出了 DSec，一个面向大规模 LLM agentic 训练、评测与环境构建的生产级 sandbox 平台。DSec 通过统一接口对外暴露多种 sandbox 后端，使用户可以针对不同的功能性、兼容性与隔离需求选择合适的执行环境。可组合的 EROFS 分层避免了重复的环境重建与解包，互补的内存共享与回收机制支撑高密度部署，QoS 感知的 CPU 调度在超卖（oversubscription）下保护延迟敏感任务，而基于 3FS 的按需镜像加载降低了镜像分发开销。DSec 还与 RL 框架集成，实现抢占安全恢复（preemption-safe resumption）与任务专属网络策略，为 agentic 负载提供可扩展的执行基础。
