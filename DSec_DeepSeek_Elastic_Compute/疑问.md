## 1. 本文到底解决什么问题？是训练还是跑 agent 业务？需要清晰的研究背景

### 结论
**服务的是训练侧（RL 采样的数据面）+ 评测 + 环境构建，不是 agent 业务/推理服务。** 一句话概括它的问题：*agentic RL 的采样吞吐，取决于能否在集群规模上便宜地造出、长时间托管、快速回收几万个异构有状态沙箱，并在 GPU 抢占下不丢 rollout 状态、不让 agent 作弊。*

### 依据
- **【原文】** §2 开头：DSec 的用户是"training frameworks、evaluation frameworks 和 data-construction pipelines"，不是终端用户或线上产品。
- **【原文】** §1 第二段：agentic 训练流水线含环境与数据构建、**RL rollout**、reward 计算、policy 更新、周期评测，"其中 RL rollout 与评测给沙箱平台的压力最大"。
- **【原文】** §6 开头：DSec 承载 DeepSeek V3.2 到 V4.1 的**所有 RL 训练与评测**所用沙箱负载。
- **【原文】** §9：推理侧沙箱（OpenAI Code Interpreter、E2B、Kimi-K2.5 Agent Swarm）被列为相关工作，论文自述差异是"那些系统多数只提到执行环境而不展开，DSec 聚焦底层沙箱基础设施"。

### 训练侧 vs 业务侧（【推断】，用于区分）
| | 训练侧（DSec 的战场） | 推理/业务侧（不是它的战场） |
|---|---|---|
| 沙箱用途 | 产出 trajectory，供 reward 计算与参数更新 | 服务一次真实用户请求 |
| 调用方 | RL 框架批量调用（单作业最多 32K 个沙箱） | 单会话，低并发 |
| 生命周期 | 中位 17.4 min、p99 超 3 小时，跨多轮驻留（§4.3） | 秒级到几分钟 |
| 吞吐指标 | 创建率、rollout 吞吐、采样成本 | 端到端延迟、成功率 |
| 关键约束 | 抢占后不丢状态；不能有 reward hacking | 多租户隔离、计费、冷启动 |
| 出错代价 | 训练信号被污染，模型学歪 | 一次请求失败，重试即可 |

### 研究背景（因果链）
1. **【原文/共识】** 前沿 LLM 从"输出文本"转向"在环境中迭代完成任务"（§1 首段），agent 能力无法靠静态问答监督得到。
2. **【原文】** 训练路径因此变成可验证奖励的 RL：rollout → reward（exit code、stdout、测试通过率等原生执行信号）→ policy update（§1 第二段）。
3. **【原文】** 负载形态随之极端化：单作业最多 32K 沙箱且短窗口内到达；90% 沙箱平均只用 ≤5% 请求 CPU；生命周期中位 17.4 min、p99 >3 h；一周 11,266 base image + 102,171 workspace、fanout 中位 3、运行时只访问镜像 4.2%–13.3% 数据（§4.1–4.4）。
4. **【原文】** 现有方案错配三条线：serverless 假设短生命周期 + 高 fanout + 镜像本地（§9）；单体 OCI 镜像导致 O(m·N)/O(k·N) 重建、只能全量拉取（§4.2、§4.4）；RL 框架把环境当黑盒、"假设沙箱总是可用且配置正确"（§9）。
5. **【原文】** GPU 集群常态抢占作业，而旧方案 agent loop 跑在可抢占 GPU pod 里，抢占即丢 rollout，只能靠 command log 回放（§6.2）。
6. **【推断】** 结论：环境从"外部依赖"变成"训练吞吐的瓶颈本身"，所以需要平台层而不是更好的 runtime——这正是论文自称 report 而非 system paper 的原因（不提出新隔离原语，§9 原话 "Rather than proposing another isolation mechanism"）。

## 2. agentic training 怎么理解？具体过程？和沙箱什么关系、沙箱是什么？

### agentic training 是什么
**【原文】** RL 训练不是喂 (问题, 答案) 对，而是让模型在**真实隔离环境**里多轮行动，用**原生执行信号**（exit code、stdout、测试通过率、任务专用 verifier）当 reward 更新参数（§1 第二段）。评测走同一执行路径，只是不回传梯度。

### 一轮训练的五段
```
① 环境构建（§6.1）  造 base image / workspace / toolkit / 测试脚本；DeepSeek 让 agent 自己造（pack_diff）
② Rollout（§1,§4.1）当前策略在沙箱里多轮：观察 → 出动作 → 沙箱执行 → 看输出，产出 trajectory
③ Reward（§1）      跑 verifier 判分：测试通过率 / exit code / flag
④ Update（§1）      PPO、GRPO 类算法用轨迹与 reward 更新参数
⑤ 评测（§1）        同一执行路径，用于衡量能力而非更新参数
```
**【原文】** rollout 与训练通过异步流水线重叠，持续补充样本以维持高并发、缓解长尾 straggler（§1）。

### Rollout 内部展开（以 SWE 任务为例，【推断】具象化）
1. 起沙箱：base image（Ubuntu + Python 3.10）+ 任务 workspace（目标 repo）+ toolkit（如 DeepSeek Harness）由 platform 组合成运行环境（§2.3）；
2. 模型看到任务描述与仓库现状，输出动作，例如 `grep -rn "def parse" src/`；
3. 沙箱执行，把 stdout 返回给模型；
4. 模型继续：改文件、`pip install`、`pytest tests/test_x.py`；
5. 直到判定完成或步数耗尽 → 得到 trajectory（全部消息 + 动作 + 观察 + 最终 diff）；
6. 判分：跑隐藏测试得 0/1 或通过率。
**【原文】** 一个沙箱大致经历 setup → tool-call → test 三段（§4.1 Fig.3）：setup 装依赖；tool-call 阶段是"短 CPU 脉冲 + 等模型出下一步"；test 阶段资源再上冲。

### 沙箱是什么
**【原文】** 一次 rollout 专用的有状态执行环境实例（§2.3），含五部分：

| 组成 | 内容 | 论文命名 |
|---|---|---|
| 文件系统底座 | OS + 语言运行时（Ubuntu / Python 3.10 / Java 8） | base image |
| 任务代码 | 仓库 + 任务专属依赖 | workspace |
| 工具 | harness、CLI、脚手架（一周 103 个） | toolkit |
| 资源与策略 | CPU/内存上限、TTL、网络允许列表（例：允许 PyPI、禁止 NPM） | resource / network policy |
| 隔离边界 | namespace / microVM / 完整 OS | FnCall / container / microVM / full VM（§2.2 Tab.1） |

**【原文】** 沙箱**全程有状态**：文件编辑、装的依赖、起的服务跨调用持续存在，后续命令看到前面命令的效果（§2.3）。这正是"内存常驻"的物理来源。

### 二者关系
**【推断】** 沙箱不是训练的附属设施，而是**采样器本身**：每一条训练样本都产生于某个沙箱会话，环境错了（跑挂、状态丢、答案泄漏），reward 就是错的，训练会学到错误行为。所以论文把安全与状态保真（§6）和性能（§5）放在同一个平台里讲。

## 3. 消耗什么资源？沙箱运行在哪里？CPU/GPU/存储怎么协同？

### 消耗的资源
| 资源 | 谁在用 | 量级（论文） |
|---|---|---|
| **GPU** | 模型前向（rollout 生成）+ 反向更新 | 不在 DSec 内；DSec 只在与 GPU 相邻处出现（GPU FnCall 为算子基准提供 GPU，§7） |
| **CPU** | 沙箱执行：编译、跑测试、装包、浏览器渲染 + 运行时开销 | 单 scale unit 30K 核（§2.4） |
| **内存** | 沙箱驻留态：page cache、可写层、进程 | 单 unit ~250 TB DRAM（§2.4） |
| **存储/带宽** | 镜像语料、写盘、远端按需读 | PB 级镜像；一周活跃工件 >130 TB（§4.4） |

**【推断】** 30K 核 / 250 TB 服务 ~380K 并发 → 平均每沙箱约 0.079 核、0.66 GB；论文未给该推算，只给"90% 沙箱平均用 ≤5% 请求 CPU"（§4.3）。
**【原文】** 成本结构的转变在于：setup 成本被突发规模相乘，而 tool-call / test 阶段长时间持有状态（§4.1）。

### 沙箱运行在哪里
- **【原文】** 独立于 GPU 集群的 CPU 集群：一个 scale unit ≈160 个 CPU 节点、30K 核、~250 TB DRAM，多个 unit 共享一套 3FS（§2.4）。
- **【原文】** 节点内：`edge`（节点代理，做本地准入、下发 eBPF 策略、拉起 runtime、TTL 回收）→ 各后端。**FnCall 与容器跑在 QEMU/libvirt VM 内**（额外隔离边界），**microVM 用 Firecracker 直接跑裸金属**，full VM 用 QEMU（§3.3、§8.1）。
- **【原文】** 网络：GPU 服务器（可信）与沙箱（执行不可信代码、可访问外网）网络隔离，唯一通路是 apiserver；sandbox ID 里编码所属 edge，故入口层无状态可水平扩展（§3.2）。
- **【原文】** 云上溢出：本地利用率 >80% 时把"镜像依赖完全落在 30 TB 去重 EROFS 集合内"的任务卸载到 200 台云 VM，吸收 ~30% 峰值（§3.4）。

### CPU / GPU / 存储协同（三条流）
```
控制面  RL 框架(GPU 侧) --libdsec--> IAM --> placement engine --> edge --> 拉起沙箱
        GPU 作业被抢占 --> RL 框架对关联沙箱发 pause --> edge 冻结(docker pause) / 快照(microVM)
数据面  沙箱执行命令 --> 观察 --> agent loop(在 DSec 侧) --> 组装 trajectory
        rollout 完成后 trajectory 交回 trainer 算 reward、更新参数
存储面  base/workspace/toolkit 在 3FS --> 元数据拉本地、数据按需读；写落本地盘 overlay upper
```
- **【原文】** 关键解耦：agent loop 不在 GPU pod 里，而在 DSec 侧的 agent sandbox + worker container 中，二者共同构成 rollout 状态的唯一真相源，被抢占的作业重连即续跑，无需 command log 回放（§6.2）。
- **【原文】** 因此 GPU 侧只负责"生成 token / 更新参数"，CPU 侧负责"环境执行 + 状态保管"，存储侧负责"字节从哪来"。

## 4. CPU 稀疏与内存常驻怎么理解？和内存池有关系吗？

### CPU 稀疏
**【原文】** 沙箱在两次交互之间常常在等模型生成下一个动作，CPU 使用稀疏——约 90% 的容器与 microVM 沙箱平均只用到请求 CPU 的 ≤5%（§4.3 Fig.5）。因此超卖是自然选择，单节点可稳定跑 ≥3,200 容器或 800 microVM（§4.3）。

### 内存常驻
**【原文】** 沙箱"闲着"但不能释放：文件编辑、装的依赖、跑着的服务、guest page cache 与宿主 page cache、可写状态都长期 pin 住（§1 第 3 条、§2.3）。生命周期中位 17.4 min（容器）/15.5 min（microVM），p99 >3 h，长寿命放大了驻留成本（§4.3 Fig.7）。
**【原文】** microVM 还有两处额外浪费：块设备数据在宿主 page cache 与每个 guest page cache 各存一份；guest 内空闲页不会主动归还宿主，因为请求容量常大于实际需求、guest 没有回收压力（§4.3）。

### 所以：超卖对 CPU 有效，对内存无效
**【推断】** 这是整篇论文的经济学核心：CPU 靠超卖把 30K 核卖出几十倍价值，而内存不能同样超卖，于是必须用"共享 + 回收 + 换出"三档手段把内存账单压下来，否则密度上不去。

### 和内存池的关系
**【原文/推断】** 基本无关。论文没有"预分配内存池再切分"的设计，用的是三档不同机制：
1. **共享**：virtio-pmem + DAX 让 guest 文件访问直接映射宿主页，多个 microVM 共用一份宿主 page cache → 峰值内存 -40.2%（§5.2、§8.4）；
2. **回收**：DAMON 采样访问位识别冷文件页并逐出，退回 buddy 后合并成高阶块，再经 balloon free-page reporting（order-9 = 2 MiB）上报，宿主 `madvise(MADV_DONTNEED)` → 时间积分内存 -21.2%（§5.2、§8.4）；
3. **换出**：暂停时 `memory.swap.max` + `memory.reclaim` 把匿名页与文件页换出，恢复时 `MADV_WILLNEED` 异步预取（§6.3）。

**【原文】** 唯一的"池"出现在别处：FnCall 的**预创建容器**与 GPU FnCall 的**预热 Python 进程池**，目的是省启动时间，不是省内存（§2.2、§7）。
**【推断】** 论文未提 KSM 或页去重；共享靠 pmem 页映射与镜像层复现，不靠 dedup。

## 5. 3FS 和 DSec 是什么关系？

**【原文】** 3FS（Fire-Flyer File System）是 DeepSeek 既有的集群级分布式文件系统，**不是 DSec 的组件，而是它依赖的外部存储**：
- 存 base image、workspace、toolkit 的只读层与 microVM 磁盘镜像（§2.4、§3.3）；
- 部署：每存储服务器 20×15 TB SSD + 2×400 Gbps RDMA；CPU 节点经 **FUSE 客户端**访问（§7）；
- 多个 scale unit 共享同一套 3FS 部署（§2.4）。

**【原文】** 3FS 的 I/O 特性直接决定 DSec 的数据面设计：**大块顺序读写吞吐高、小块随机 I/O 差**（§5.3），由此推出三条规则——① 写留本地（overlay upper 落本地盘，避开小写惩罚）；② 读按需且批量（只在实际访问时取，靠内核 readahead 合并成大请求）；③ 元数据尽量本地（EROFS 多设备模式把 fs metadata 下载到 worker 本地，路径查找不产生远端 I/O）。

**【原文】** 具体落法：容器镜像离线从 OCI 转 EROFS（元数据/数据分离）；microVM 用 OverlayBD over 3FS + ublk 用户态块设备，256 KiB 取块 + 二级本地缓存，因 ext4 元数据仍嵌在块镜像里，元数据读仍可能触发远端 I/O（§5.3）。

**【原文】** 选 3FS 而非 registry + P2P 的理由：复用已有训练存储、避免再运维一层镜像分发系统；对比 Nydus 是 userspace 后端（fscache/FUSE）从 registry/对象存储懒加载（§5.3、§9）。

**【外部】** 3FS 主要为 AI 训练的大块批量读设计，同时提供 FUSE 客户端与原生（zero-copy）客户端；DSec 用的是 FUSE 路径（§7），因此绕开 FUSE 元数据路径、把元数据放本地就更重要。
**【原文】** 论文**没有**给出小块随机 I/O 的具体劣化量级（如 4 KiB 随机读的 IOPS/延迟对比），这是第 5 条待核实项。

## 6. 内存共享是什么意思？

三个层次，论文只讲前两个：

### ① 宿主 page cache 共享（性能实测的那一层）
**【原文】** 传统 microVM 走 virtio-blk：镜像数据先缓存进宿主 page cache，再拷贝进每个 guest 的 page cache，同一份数据两份。改用 virtio-pmem + DAX 后，guest 的文件访问直接映射到宿主后备页、不拷进 guest RAM，同宿主的多个 microVM 共享**同一份宿主 page cache**（§5.2、§8.4）。代价：冷访问可能触发同步缺页；guest 需为整个 pmem 区间分配 `struct page` 元数据，占容量 1/64（128 GB pmem → 2 GB guest RAM），故只用于只读 EROFS 层。

### ② 镜像层共享（磁盘与缓存双重节省）
**【原文】** overlayfs 只读 lowerdir + EROFS：几千个沙箱引用同一 base/workspace 层时，磁盘只有一份；配合 ① 内存里也只有一份 page cache。可组合层之所以成立，前提就是"共享的是层，不是整个镜像"（§5.1、§5.3）。

### ③ 运行期状态不共享
**【原文】** 可写层（overlay upper）每沙箱私有、落本地盘；沙箱之间互不可见（§5.1、§5.3）。**【推断】** 这是必须的：共享可写状态会让任务互相污染、答案泄漏，直接破坏训练信号有效性。

### 容易混淆的一点
**【原文】** §6.2 的 "single source of truth" 指 rollout 状态由 worker container + agent sandbox 共同持有（生命周期概念），**不是内存共享**，别混为一谈。
